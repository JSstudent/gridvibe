# Changelog

All notable changes to GridVibe will be documented in this file.

## Unreleased

- **(feat) The pane's reset button now starts an agent, not just a shell.** The 🔄 dropdown on a Local Repo pane already listed **Command Prompt**, **PowerShell**, **WSL** and every detected distro; each of those rows now carries a chevron on its right that opens that shell's agent list — **Plain shell** plus Claude, Codex, Copilot, OpenCode, Kilo, Kimi, Grok and Hermes. Picking one relaunches the pane under that shell *and* starts that agent, so “this pane, but Codex in WSL” is one click instead of a relaunch from the launcher. Pressing the shell row itself is still the plain relaunch it always was. **SSH panes get the same list**, and this is new for them: they had no dropdown at all before, because they have no shell family to pick between — they now get **Reset view** plus the agent list flat under an **Agent** heading, as does a Local Repo pane on a non-Windows host. **Plain shell** on a pane that is running an agent drops the agent and comes back to an ordinary prompt, which there was previously no way to ask for. Clicking whatever the pane already runs does nothing, so a live shell is never killed by a stray click, and the pane keeps its slot, title and group throughout. Auto mode follows the agent rather than the pane: relaunch the same agent under another shell and it stays on; move to a different agent and it starts from that agent's plain launch, since a flag registered for one CLI says nothing about the next. Explorer and browser panes have no shell to relaunch and keep the plain one-click reset.

- **(fix) An agent's install command no longer runs off the edge of the card, and there is now a button to copy it.** The **Check** panel in Terminal Setup prints the install command for whichever agent and environment the pane is pointed at, and a command containing a long web address had its tail cut off at the card's right edge — Hermes' installer was the worst of them, but Kimi's clipped too in a narrow pane, and any future agent with a long address would have. A web address has nowhere to break, and the box would not let it. It now wraps inside the card, so the whole command is readable for every agent in every environment. The command also sits on its own line under the label now, with a copy button on the label's row lined up with the card's right edge: one click puts the exact command on the clipboard and the button ticks over to confirm it. If the copy is refused — some browsers block it on an insecure address — you are told, instead of the button pretending it worked.

- **(feat) Grok Build and Hermes Agent joined the agent list.** Both now sit in the launcher's startup dropdown beside Claude, Codex, Copilot, OpenCode, Kilo and Kimi, with everything the others already have: the per-target **Check** that says whether `grok` or `hermes` is on `PATH` in the environment the pane will actually run in (Windows, the chosen WSL distro, or the remote host over SSH), the install command for that environment when it isn't, and the **Auto mode** toggle — `grok --always-approve` and `hermes --yolo`, each described in the toggle's own help text. They save and restore through sessions and workspaces like any other agent, and starting either one by typing it at a shell prompt promotes that pane to an agent pane the same way. GridVibe does not install them: Grok Build is `irm https://x.ai/cli/install.ps1 | iex` on Windows and `curl -fsSL https://x.ai/cli/install.sh | bash` elsewhere, Hermes is `iex (irm https://hermes-agent.nousresearch.com/install.ps1)` and `curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash`, and remote hosts stay detect-only as they are for every agent.

- **(fix) Find now marks the right text in Windows-line-ending files.** Searching a file saved with CRLF endings — most files written by a Windows program, and every one of the JSON state and log files these tools keep — put the highlights further and further from the actual matches the deeper into the file you went: about a character per line, so line 100 was off by 99 and the end of a 900-line file by 900. Near the top it looked like a slight smear, in the middle it tinted unrelated text, and towards the end the marks disappeared entirely and next/previous had nothing to scroll to — while the `1 of 42` counter stayed perfectly correct, which is what made it look as though only the scrolling was broken. The syntax colours were read back out of the browser's own HTML parser, which quietly rewrites every CRLF to a plain newline before anything can be measured, so the colours were being counted in a file one character per line shorter than the one being searched. They are now read straight from the highlighter's output, with the length checked against the file, by the same code that already did this for files over 64 KB — which is why large files were unaffected and only small and medium ones showed it. Files with Unix line endings behave exactly as before.

- **(fix) An apostrophe no longer miscolours the rest of the line in text and Markdown files.** Writing "version's interval" in a `.txt` or `.md` file turned everything from the apostrophe onwards into string colour, and a paragraph full of contractions came out looking like a paragraph of code — because the highlighter that handles the file types the syntax engine does not carry read `'` as the opening of a quoted string, the way it is in real code. In prose it is a letter, so it no longer opens anything there. Everything else in those files is coloured exactly as before: numbers, double-quoted phrases and Markdown's backticked inline code are not ambiguous, and `'` is still a string quote in every language where it is one. Separately, a quote that never closes now stops at the end of its own line instead of running to the end of the buffer — one apostrophe in a fenced code block used to colour every line below it.

- **(fix) The Files tree now comes back where you left it, not on the file Preview happens to be showing.** Which folders you had open has been saved with the session and the workspace for a while, and so was how far down the tree you had scrolled — but the tree finished restoring by expanding the path to whatever file the Preview tab was on and scrolling that row into view, so the position was put back and then immediately overwritten. It now expands the ancestors as before and leaves the scrolling to the restore. A pane opening for the first time still reveals the file it is showing, since there is nothing else to point at.

- **(fix) Uploading, deleting or renaming a file no longer throws the Files tree back to the top.** The tree is re-read after any of those, and after a Git action, and the re-read emptied the panel — which parks the scrollbar at 0 and, worse, saved that 0 as your position, so the offset the refresh was about to put back was already gone. Uploading one file into a folder deep in a large tree meant scrolling back down to it every time. The folders you had open were already kept; the place you were reading now is too.

- **(feat) You can now upload files into the file explorer.** Downloading has been there for a while and had no counterpart, so getting a file *into* a remote host meant leaving the grid. Upload is now offered everywhere download is — the file view's toolbar, the Files tree, the Preview listing, the tab strip and the Git sidebar's rows — plus the places download has no reason to appear: every folder row, the blank space of both the tree and the listing, and a button in the explorer bar for whatever folder the pane is showing. A folder uploads into itself, a file uploads into the folder it sits in, and the menu entry names the folder it found before you click it, so it can never land somewhere you were not looking. Local repo panes and SSH panes alike, and in the native window the picker is the desktop one. Select as many files as you like: each is its own transfer, capped at 100 MB, with one confirmation past ten files and one result at the end rather than one per file. A file the server would refuse — no name, a path separator in it, over the cap — is named before anything is sent, so it is not one more red line in the report.

- **(feat) Uploading a file that is already there keeps the old one and numbers the new one.** The first version of this refused the upload and told you to rename the file first, which is backwards: the reason to upload a name that already exists is almost always that this one is newer, and the previous version is worth keeping until you say otherwise. `report.pdf` uploaded a second time becomes `report (1).pdf` beside it, then `report (2).pdf`, keeping the extension where it belongs. The existing file is never opened, let alone written to — every candidate name is taken by an exclusive create, so two uploads racing for one name each get their own. The result says which name it used ("report.pdf was kept as report (1).pdf"), because a rename you are not told about is worse than the refusal it replaced. Deleting the old one and renaming afterwards is one gesture each; a version overwritten is not recoverable at all.

- **(feat) A commit row's tooltip and its right-click menu are now one card, opened by the right-click.** The card used to appear on its own while you were only running your eye down the subjects, and it carried the facts but nothing you could do with them; the right-click carried **Copy commit hash** and **Copy commit message** but told you nothing about the commit. One row answering to two gestures, each with the other half of the answer. Right-clicking a commit now opens the card, with a copy button beside the message and another beside the full object id. Hovering a row does nothing. The card is wide enough to show the forty-character id on one line whatever the sidebar's width, opens above the row when there is no room below it, and closes on `Escape`, on a click outside it, after a copy, or when you scroll the graph underneath it. The keyboard's context-menu key opens the same card, and the row itself still reads out the same facts for a screen reader.

- **(fix) Search results now open large files at the result, not at the top.** Clicking a hit from the repository search (`Ctrl+Shift+F`) in a big file dropped you at line 1 every time, with no flash on the line and no highlight on the matched text — while the same search in an ordinary file went straight to the hit, which is what made it look like only some results were broken. A file over roughly four thousand lines is drawn a few frames at a time so the pane stays responsive while it opens, and the jump to the result was made before any of those lines existed: it looked for the line, did not find it, and quietly did nothing. It now waits for the file to finish drawing and then goes to the result — centred, flashed and with the matched text tinted, exactly as in a short file. Short files are unaffected and still jump immediately. If you switch that pane to another group or open something else while the file is still drawing, the jump is dropped rather than applied to whatever is there now.

- **(fix) The wrap-lines button now works in Source view.** It drew itself, labelled itself and showed the right pressed state over a source file, and clicking it did nothing — every source file, of every type. Wrapping was added to Source everywhere the feature is built (the view itself, the in-place editor, the per-tab record and its saving) except in the button's own click handler, which still listed only Markdown preview and Diff. Pressing it now toggles Source wrapping like the other two, and the choice rides along per tab through Save Session and Save Workspace as it always should have. Preview and Diff are unchanged.

- **(fix) Opening a large file's diff from the Git sidebar no longer flickers.** Clicking a changed file or a commit's file row drew the diff, then tore it down and drew it again about a tenth of a second later — long enough to see the lines jump, and long enough to lose any scrolling you had already done. The delay was never the patch's: it was the *source* view finishing its own render behind the panel, which then asked for the diff a second time, and a one-line change to a 7,000-line file went through it while the same change to a short file did not. The Diff panel now knows what it is already showing, the way the Markdown preview and the source view already did, and a request to draw what is on screen draws nothing. Anything that genuinely moves the render — a new patch, a different commit, toggling line wrapping, a save — still redraws it in full.

- **(fix) The Diff view no longer indents code away from the line numbers.** A file whose lines are short — one or two words, a list, a plain log — showed a wide blank strip between the line number and the code on both sides, and the strip was a different width on each side, so the two columns did not line up. The line-number gutter is a fixed 4em, but the diff's table hands out whatever width is left over between its columns, and once the code is narrower than half the pane there is a lot left over: the gutter's column took a share of it while the gutter itself stayed 4em, leaving the remainder as dead space. The code column now claims that space, so the gutter stays 4em and the code starts right beside it whatever the lines contain. Long lines are unaffected and still scroll horizontally per side.

## 1.10.0 - 2026-08-30

- **(feat) The Git graph reads further back on demand.** Graph has always shown the newest 60 commits in the selected scope, which is also everything the commit find can search — so a search that came up empty could not tell you whether the commit was absent or merely further back than the page you had. **Show more** at the end of the list reads another 60 each time, up to 300, and every request the sidebar makes afterwards keeps the page you expanded to, so staging a file or committing no longer collapses the graph back under you. When there is nothing left to load the button is replaced by the total it ended on, and at the 300 ceiling it says the graph stops there rather than implying the history does. A find that matches nothing now says so in both subject and id mode, right above the control that widens the search.

- **(feat) Hovering a commit row shows who wrote it and when.** The row has space for an abbreviated hash and a truncated subject, and the tooltip behind it was the same one line again. It is now a card in the app's own styling: the full message, the author, the date with a relative age beside it, the full object id, and any branch or tag decoration on the commit. The date is shown in the author's own time zone, the way `git log` shows it, so a commit never appears to move to another day for someone reading from elsewhere. A field the repository did not record is left out rather than shown as unknown, and the card opens above the row when there is no room below it, so the last commits in a scrolled list are not cut off.

- **(fix) Saved sessions now relaunch with their Git pin and Follow scope.** Both the launcher and the in-workspace saved-session menu wrote the pin, Follow flag, and Preview location correctly, but their shared final launch-field builder omitted the pin and Follow fields before creating the replacement panes. Relaunching therefore fell back to the explorer root even though the preset on disk was intact. The shared launch boundary now carries the complete Git scope record for explorer panes and still strips it from terminal, agent, and browser panes.

- **(feat) The Files tree now shows where Follow Git browsing is pointing.** The pinned row has been marked for a while; Follow had nothing, even though it is the control that moves — it is a mode with no fixed path, so the only thing saying it was on at all was a pressed button in a sidebar you may not have open. The row Follow is tracking now carries the same chain icon the button wears, and it moves as you browse. A row that is both pinned and followed shows both marks, because turning Follow off lands you back on the pin. Following the explorer root marks the **Files** header, and following something currently collapsed out of sight shows no mark — the tree still never expands itself to reveal one, and the repository bar still names the scope either way.

- **(feat) The Git sidebar's repository bar stays put while you scroll.** Repository, branch, and the pin and Follow rows are what every change row and every commit below them is read against, so scrolling them away left a long graph ambiguous about what it was a graph of. That bar is now frozen at the top of the sidebar. **Publish**/**Push** moved out of it into its own row immediately below and scrolls away with everything else — it is the one action there that reaches a remote, and keeping it under the pointer at every scroll position is not what freezing the header was for. The Graph's commit find stays pinned too, now sitting just under the frozen bar rather than sliding behind it.

- **(fix) The Preview tab now offers Copy path, Copy relative path and Download.** Right-clicking a pinned tab has always offered them, and right-clicking the Preview tab already offered to pin Git to the file it was showing — but not to copy or download that same file, so one tab in the strip named a path it would not spell. Every tab that names a file now carries the same path entries, the Preview tab included. Showing a directory listing it still names no file, and no tab offers the create/rename/delete actions the tree and the listing do.

- **(fix) Follow Git browsing now follows the row you pointed at.** Choosing **Follow Git browsing** on a file in the Files tree or the Preview listing scoped Git to the folder the listing happened to be showing, not to the file you had right-clicked — the **Pin Git here** entry beside it had always named the row. Follow now names the row first and follows that, and it stays there until you browse somewhere else, at which point it goes back to tracking what you open. Highlighting a single row with `Ctrl`-click is treated the same way, which is what the Graph header's own chain button reads: it has no row of its own, so highlighting a file and pressing it follows that file rather than whatever is open in Preview. Clearing a highlight with `Escape`, or right-clicking a row without selecting it, changes nothing — only navigating away does.

- **(fix) Follow Git browsing is offered per row, on the same two rules the pin is.** With several entries selected the entry now disappears, exactly as **Pin Git here** already did: Follow is one exact path, and picking one of the selected rows would be picking arbitrarily. And every row now asks whether Follow is *here* rather than whether Follow is *on* — only the row Follow is actually on offers **Unfollow Git browsing**, and any other row offers to move Follow onto it in one action. Following a folder used to leave no way to say "follow this file" short of switching Follow off, browsing to the file and switching it back on.

- **(fix) A Git pin follows the file or folder it names through a rename.** Renaming something moves it; it does not remove it. Every other path the pane is holding already followed — the folder you are browsing, the open file, the tab strip, the folders you had expanded, an in-place edit — but the pin stayed on the old spelling and the sidebar then reported that the path no longer exists, about a path you had just watched move. Deleting the pinned path still leaves the pin naming it, with **Clear pin** beside it: a deleted path cannot be followed anywhere, and quietly widening the scope back to the explorer root is the one thing worse than saying so.

- **(perf) Right-clicking in the file explorer no longer waits on a Git request to open the menu.** The **Pin Git here** entry has to know whether the row is inside a worktree, and asking the server every time meant a right-click highlighted the row and then showed nothing at all for the length of a `git rev-parse` and `git status` — over SSH, a noticeable pause on every single right-click, including on blank space. When the sidebar has already loaded a repository that contains the explorer root, every path under it is inside that repository and the menu opens immediately. Anything the loaded repository genuinely cannot answer — a pane whose sidebar has never been opened, a repository that sits *below* the explorer root, and anything inside `.git` — still asks, so a row outside a worktree is still greyed out with a tooltip saying why. Two quick right-clicks can no longer land the first one's menu on top of the second's.

- **(fix) A pinned file is named in full wherever the scope is named.** The repository bar has room for a file's name and not its folders, so it shows the name — but so did every tooltip built from it, and two files called `api.py` in different folders are one word for two different scopes. A pin you cannot tell apart from another one reads as a pin that was lost, which is the exact failure the scope row exists to prevent. The row still shows the short name; hovering it, the **Clear pin** button, the pin button's "pinned: …" and the bulk action tooltips all now spell out the whole path.

- **(fix) Searching the Git graph for something that is not a commit id says so.** Hash mode refuses a non-hexadecimal query rather than searching it as a subject, which is right — but it then reported the refusal as "No commit in the loaded graph", inviting you to scroll for a commit that was never an id in the first place. The two empty results now read differently.

- **(feat) The Git pin and Follow now go down to a single file.** Both controls used to name a folder and nothing smaller, so "show me this file's history" meant reading its commits out of the containing directory's graph. Pin a file — from the Graph header while it is open in Preview, or from the right-click menu on any row — and the Graph, the Changes lists and every Git action narrow to that one path; the repository bar names the file. **Follow** does the same thing live: with it on, opening a file scopes to that file and opening a folder widens back to the folder, and switching tabs re-scopes as you go. A pin remembers *what kind of thing* it points at as well as where, so a file pin survives Save Workspace, restart and restore as a file pin, and a file that has since been deleted is reported by name with **Clear pin** beside it rather than quietly widening to its folder.

- **(feat) Bulk Git actions obey a file scope, which makes them narrower than their names suggest.** This is the surprising half of the file pin, so the sidebar states it: with a file scoped, **Stage All**, **Unstage All** and **Discard All** act on that one file, and their tooltips name the scope they will act in. **Commit** is the exception that refuses instead of narrowing — committing only part of what you have staged would be a silent partial commit, so if anything staged lies outside the scope it declines and tells you to widen the scope or unstage those paths. **Publish** stays branch-wide, because it pushes commits that already exist rather than touching the index or your working copy.

- **(feat) Pin Git from the right-click menu, in the Files tree and in the Preview listing.** Scoping Git no longer requires browsing to the target first: right-click any folder or file and choose **Pin Git here**, or **Unpin Git** on the row that *is* the pin. Both filesystem browsing surfaces offer it — the Files tree and the directory listing in the Preview tab — along with **Follow Git browsing**, so the same row means the same thing wherever you right-click it. The entry is single-target by design: select several entries and it disappears rather than pinning one of them arbitrarily, and a commit row in the Graph still offers only its two copy entries, since a commit names a repository object and not a path. A row that is inside no repository keeps the entry in place, greyed out, with a tooltip saying why.

- **(fix) The Files tree comes back expanded as you left it.** Which folders are open is saved; the folder listings behind them are not, because fetched data is never persisted. On restore the tree re-read only the folders leading to the file or directory the pane was showing, so every other branch you had opened came back as a chevron pointing down over nothing at all — a tree that read as collapsed while every arrow said otherwise, and the reason a restored pin could look like it had landed on an empty folder. The tree now re-reads the branches you left open, working down from the root so a folder is only fetched once its parent confirms it still exists; a folder that was deleted or renamed since the snapshot is dropped from the saved set instead of being requested. Re-opening a folder you had collapsed brings its restored sub-branches back with it, and the tree's scroll position is put back once the branches it belongs to exist.

- **(fix) The Git graph follows the file you open straight away.** With **Follow** on, walking into another folder re-scoped the sidebar immediately but opening another file did not — the graph sat on the previous scope until the background change listener next noticed, so the same gesture felt instant in one direction and laggy in the other. Opening a file is now treated as the scope change it is. Navigation that leaves the scope alone — browsing with Follow off, or re-opening the file already scoped — now costs nothing at all, where it used to redraw the whole Git panel and take the caret out of a commit message you were typing.

- **(feat) Git's Clear pin is now offered wherever a pin is, the pinned folder included.** It used to hide as soon as you walked back onto the folder the pin was on, on the reasoning that the pin button is pressed there and a click clears it — so the *named* control went missing at exactly the folder you are standing in when you decide to unpin, and the only way out was a button whose pressed state had deliberately stopped meaning "a pin exists" everywhere else. **Clear pin** is now on the pin's row whenever there is a pin, and clears it in the same single write the button does; the button keeps its shortcut at the pin and still never clears a pin you made somewhere else. Browsing in and out of the pinned folder no longer moves the control you were reaching for.

- **(fix) Staging a Markdown file no longer strands its Preview on "Rendering preview...".** Staging a file you have open re-reads it, and because its working-tree diff is now empty the pane drops back to the content view — Source for most files, Preview for a Markdown file you had been previewing. The re-read drops the pane's cached render and asks for it again, but the panel was still stamped with the render it had been showing, and the answer that came back was identical to it — so the paint read as "already on screen" and did nothing, leaving the loading message with nothing on screen able to replace it. The panel now gives up that stamp whenever anything other than a finished render is put into it, so the render that arrives is always painted. The same dead end could be reached from the "file changed while the preview was rendering" notice and from a failed render.

- **(fix) Folder names and folder chevrons in the Files tree now have separate jobs.** Clicking a folder's name opens it in Preview without changing the saved tree structure; only its chevron expands or collapses it. Navigating inside Preview still follows the destination in the tree by expanding the ancestors needed to reveal it, while leaving the destination folder itself collapsed until its chevron is clicked. Existing expanded-folder persistence is unchanged.

- **(feat) The Git pin button now asks "is the pin *here*", not "is there a pin".** It used to be a two-state toggle on the pin's *existence*, which made pinning a second folder a three-step gesture — navigate anywhere, click to unpin, navigate, click to pin — and left the pane sitting at an unpinned scope in between, reloading the whole graph for it. Worse, the pressed state was the pane's only report that a pin existed, so the button read as "pinned" while you stood in a folder that had nothing to do with the pin. Now that the Files tree marks the pinned row and the repo bar names the scope, the button answers the question it is actually next to: it is pressed only while you are browsing the pinned folder, where a click clears it; from anywhere else it wears a distinct outline, its tooltip names where the pin currently is, and a click **moves** the pin here in one action — one graph reload, no flash through an intermediate scope. It never clears a pin you made somewhere else. Clearing from a distance is the repo bar's **Clear pin**, which is always reachable, so a pin on a folder that is collapsed, deleted, or outside the current root can still be cleared. Walking between folders repaints the button on the spot, without disturbing a commit message you were typing.

- **(feat) A Git pin and a live Follow are shown as two rows, not one.** The repo bar showed the scope that was *in effect*, so with Follow on it named the folder you were browsing, wore the chain icon — and still carried **Clear pin**, an action about a path that was nowhere on the row. Nothing said where the pin was or what Follow was tracking. There is now a pin row whenever a pin is set and a Follow row whenever Follow is on, both when both are, and **Clear pin** only ever sits on the row that names the path it clears (its tooltip names it too). While Follow is on the pin row dims and says it is overridden rather than disappearing, because turning Follow off lands you straight back on it.

- **(fix) Long Git sidebar headings are now split into icon-labelled rows.** The repository folder, branch, and pinned or followed directory each get their own line, so a deep scope no longer crowds the whole heading.

- **(feat) The Files tree shows which folder the Git scope is pinned to.** A pin freezes on the folder you made it in, so navigating away used to leave nothing on screen saying where it was — a restored workspace that came back somewhere else read as a pin that had been lost. The pinned folder's row now carries a pin mark beside its open-in-folder button, and a pin on the explorer root marks the **Files** header, which is what the tree shows in place of a root row. The mark moves without the tree re-rendering, so your scroll position and open folders are untouched, and it appears in the filtered tree too. A pin on a folder that is currently collapsed out of view shows no mark — the Graph header still names the scope, and the tree never expands itself to reveal it.

- **Internal — the Files tree now owns its own module.** Files-tree state,
  loading, row markup, folding, reveal and refresh moved byte-identically from
  `explorer-viewer.js` into `explorer-tree.js`, which is loaded immediately
  after the viewer and shares its classic-script scope. The viewer side is a
  pure deletion; the existing behavioural contracts and the local/SSH manual
  smoke test passed with no user-visible behaviour change.

- **(fix) Leaving the explorer clears *both* of the Git sidebar's scope controls.** Switching a pane to a terminal already dropped a fixed pin, because a pin names a folder relative to the explorer root it was made under. **Follow browsed folder** was left on — and that turned out to matter more, not less: reopening the explorer lands the pane wherever the shell has walked to, so Follow immediately scoped the Git sidebar to a deep subdirectory of a root you never chose, with the chain button pressed and no pin on screen to explain it. Leaving the explorer now clears the whole scope selection. Restoring a workspace still brings both controls back, and re-pointing a saved row's directory in the launcher still drops the pin alone — a relaunched pane opens at its root, where Follow is indistinguishable from no Follow.

- **(fix) Saving a workspace no longer clears pane settings it was never told about.** Save Workspace writes what the page describes, and the description is filled in with defaults for anything it leaves out. Those defaults were then applied back to the live panes — so a save that did not mention the Git pin, the expanded commits, or any other explorer view state silently switched it off on the running pane, even though the saved preset itself was fine. The pin looked like it had been lost at random, and was one of the reasons the whole thing felt flaky. A save now only changes the live pane for the settings it actually stated; silence leaves the pane alone. Only the page can say a pin was cleared.

- **(fix) A Git pin on a folder outside any repository now says which folder.** Pinning a folder that is inside no worktree is allowed, and the pin was saved and restored faithfully — but all you saw afterwards was "Folder is not inside a Git worktree", with no indication of *which* folder was being asked about. Restoring a workspace with such a pin was indistinguishable from the pin having been lost. The sidebar now names the pinned path and offers **Clear pin** beside it.

- **(fix) A Git pin on the explorer root is visible as a pin.** Pinning while browsing the root itself is a real pin, and it asks the server for exactly what an unpinned pane asks for — so a perfect save and restore looked, on screen, like the pin had quietly gone. The Graph header now names the selected scope, `root` included, so a pinned root reads as pinned and a followed folder reads as followed.

- **(perf) A pinned Git sidebar stops reloading the whole repository in the background.** The sidebar remembered which scope it had loaded by the folder the *server* resolved, and the server answers with the path relative to the repository it found — which is rarely the same text as the pinned path that was asked for. Every background check therefore looked like the scope had just changed and refetched the repository, its branch, its status and its commit graph. It now compares what it asked for with what it asked for, so an unchanged scope costs one small state check as intended.

- **(fix) The launcher says when editing a row's directory drops its Git pin.** Changing the directory on a saved row re-roots the pane, and a pin belonging to the previous root cannot be carried across — so it is dropped, correctly, and silently. The launch notice now mentions it once, naming the rows affected, folded into the same message that reports the launch. It goes out as a warning rather than an informational note, because it reports state that has been thrown away and an informational note dismisses itself after six seconds; a row you never titled is named by its position in the form rather than by its position among the rows that were affected.

- **(feat) Collapse the Git commit graph in one gesture.** `Alt`-click any commit row or its chevron to close every expanded commit in the loaded Graph. The gesture is collapse-only — using it on a graph that is already closed never expands all of the commit file lists — and the commit-message box keeps its text, focus, and caret while the rows close.

- **(fix) Changing a setting no longer lands halfway through something GridVibe is already doing.** Settings are saved as one whole set, but a few operations read them one value at a time — so saving App Settings at the wrong moment could leave a single action using two different versions. A pane refused for being over the session limit could quote a *different* limit than the one it was refused against, telling you to raise a number that was already high enough. Voice input could start the engine named by a version other than the one that allowed it to start, and the message after installing the voice dependencies could name one engine while reporting whether a different one was ready. - **(fix) A retired shell can no longer report where it was after you replaced it.** Switching a pane's shell, or switching it between terminal and explorer or browser, deliberately forgets where the old shell was standing — its last report says nothing about the new one. But the shell being replaced can still have a final prompt in flight at that moment, and that prompt carries a directory: it could land just after the switch and put the old directory back. A pane could then seed the file explorer, or be saved into a workspace, pointing at somewhere nothing live was standing. A directory is now only recorded while the shell that reported it is still the pane's shell. Nothing else about the reading changes — it still costs no keystroke at your prompt and still works during a build, a pager, a TUI or a running agent.

- **(fix) Finishing an action after you switch session no longer disturbs the pane that took its place.** A grid position is not a pane: switch to another session while **Reset view** is waiting for the terminal's scrollback, or while a Git sidebar action is still running, and a different pane is sitting in that position by the time the answer arrives. The mouse-reporting reset could then be written into that pane instead of the one you asked, and a finished Git action could repaint it, reload its folder, or refresh the file it had open. Every such finish is now addressed to the pane that started it: the reset reaches your terminal even though it is no longer on screen, and the pane that replaced it is left alone. The **Refreshing…**/**Clearing…** state clears on the pane that was busy rather than on whatever now occupies the slot, so a session you come back to is not stuck mid-refresh. And if a Git action lands while its session is in the background, that sidebar reloads for real when you return rather than showing a repository state that has moved on. In the Git sidebar the same applies to the scope you are looking at: changing the pinned or followed folder while an action is running no longer lets the previous folder's answer overwrite what is on screen — the current folder is loaded instead. The action itself is never cancelled or repeated; it was already sent, scoped to the folder it was started from.

- **(fix) Narrowed Git sidebar actions no longer change hidden sibling paths.** Stage All and Unstage All now apply the selected root, Pin, or Follow pathspec instead of the whole repository. Discard All discovers and restores only tracked, non-conflicted worktree changes in that scope, while continuing to preserve staged content and every untracked file. A Commit from a narrowed scope now refuses when anything staged lies outside it and tells you to switch to repository-root scope or unstage those paths; Publish remains branch-wide because it pushes existing commits rather than changing the worktree or index.

- **(fix) Output-limited Git commands no longer masquerade as success.** Local and SSH runners now report completion separately from stdout/stderr truncation and output-limit termination, retaining an exit status only when Git actually supplied one. Status, graph, commit-file and repository-state reads reject incomplete data, and every mutation reports that repository state may have changed, requests a refresh, and is never retried automatically. Repository search and bounded diff remain the only explicitly partial responses and continue to label their truncated output.

- **(fix) Restored SSH terminals no longer print GridVibe's startup plumbing.** The remote working-directory hook and restore `cd` still run exactly as before, but their PTY-echoed command lines are removed from the initial console output before it is cached for replay. Cleanup is one-shot and SSH-only: local cmd, PowerShell, WSL and normal terminal output never enter it, while an unsupported or slow remote shell fails open after a short bound and shows the original output instead of hiding diagnostics.

- **(fix) Find works in a very large file's own diff.** A file big enough for the plain large-file view turns Find off, because that view has no per-line rows to point at. That verdict was applied to the whole pane, so the file's **Diff** tab — a patch of a few lines, and bounded however large the file is — had no find box either. This was already fixed for a commit diff opened from the Git sidebar; the file's own diff now behaves the same way. Source and the Markdown preview of such a file still have Find off, and still say so — and on those two panels `Ctrl+F` now falls through to your browser's own find instead of being swallowed by a box that could not answer.

- **(fix) The Markdown preview says so when it gives up.** If the file changed in the moment between GridVibe reading its text and rendering its preview, the panel was left showing "Rendering preview…" with nothing to click. It now says what happened and offers **Refresh**, which reloads Source and Preview together.

- **(fix) A folder with a `%` in its name no longer breaks directory tracking.** The sequence a POSIX terminal's prompt uses to report where it is treated a `%` in the path as a formatting instruction, so bash/zsh/WSL and SSH panes sitting in such a folder reported nothing usable — and the explorer opened somewhere else, or said it could not tell. A folder whose name contains a literal `%2F` was misread as two folders for a related reason. PowerShell and Command Prompt used a different sequence and were unaffected; a shell that emits its own directory sequence is still read exactly as before.

- **(perf) Switching a pane away from a large file stops the work it was doing.** A file big enough to be painted over several frames kept painting after you switched the pane to a terminal or a browser preview, into a view nobody could see and in competition with the one that had just replaced it. Background syntax colouring for that file kept running too. Both now stop when the pane does.

- **(fix) SSH agent commands reach the shell before fallback directory observation.** When shell integration had reported a remote shell pid but not its directory, recognizing a manually started agent could spend up to the bounded remote-directory timeout before forwarding Enter, and a later keystroke could overtake it. GridVibe now sends the input first, then records the agent metadata; successful promotion and Save Workspace directory restore are unchanged.

- **(perf) Editing a large file no longer stalls a moment after you stop typing.** Typing in the in-place editor was made cheap a while back: only the lines you actually changed are rebuilt. But the pass that fills the real syntax colours back in — which runs a beat after the last keystroke — still rebuilt every line in the file to do it, so a long file hitched about a second after each edit, just as the colours arrived. Only the lines whose colours genuinely changed are repainted now, which for an ordinary keystroke is one of them.

- **(fix) Very large diffs no longer misread lines that look like a file header.** A changed line whose text begins with `--` or `++` — a `---` rule or front-matter marker in Markdown, a `--flag`, a `++i;` — was mistaken for the `---`/`+++` header at the top of a patch and left out. Worse than the missing line, everything below it kept the numbering it would have had, so the rest of the file was shown under the wrong line numbers with unrelated lines paired against each other. This only affected diffs large enough for the plain side-by-side view, which is exactly where it is hardest to spot.

- **(fix) Leaving the explorer clears its fixed Git pin.** A pin names a folder relative to the explorer root where it was created. Keeping it while the pane became a terminal meant you could `cd` to another repository, reopen the explorer there, and still have the Git sidebar locked to a path belonging to the previous root. Entering terminal mode now clears the fixed pin, so the next explorer starts from its newly resolved root/current folder. A workspace saved while still in explorer mode restores its pin as before.

- **(fix) Reopening the explorer no longer leaves its Preview on the previous root.** After browsing a subdirectory, switching to the terminal, moving elsewhere, and reopening the explorer, the Files tree followed the terminal but Preview retried the directory saved under the old root and stayed on a “no longer exists” error until you clicked the tree. A live mode switch now opens the terminal's freshly resolved directory relative to the new root; workspace startup still restores its saved Preview directory as before.

- **(fix) Explorer navigation no longer resets the Git sidebar's scope.** The Git graph, status watcher, and all eight actions start anchored to the explorer root chosen in the launcher or derived from the terminal's working directory. A new pin beside Graph search captures the current folder as a fixed Git scope, so a repository below a non-Git explorer root can become the anchor without changing filesystem confinement. The independent chain button opts the pane into following the browsed folder; when both are active, disabling follow returns to the pin. Both controls are off by default, persist through workspace save/restart, and every read and action uses the same selected scope.

- **(fix) The file explorer follows the terminal back *up*, not only down.** Opening the explorer from a pane you had `cd`-ed into a subdirectory worked; going back to the terminal, walking back up, and opening the explorer again reopened it in the subdirectory. Two things kept it there. The explorer will not widen its view above the folder you picked when you launched the pane — but that folder was being read from a value every mode switch overwrites, and it was not saved with the workspace either, so after one trip through the explorer, or after a restart, the pane believed it had launched wherever it had ended up and walking up looked like widening. And a workspace saved with such a pane brought the worked-out root back as though you had chosen it, pinning the pane for good after a restart. GridVibe now remembers where a pane was actually launched and saves that alongside where the pane is, so the same pane in the same folder opens the same explorer before and after a restart. The widen guard applies only while the pane is still inside that folder — a shell that has walked further up is somewhere on purpose. And whether anybody picked a root is now recorded against the root actually stored: a pane whose shell has walked outside the root you chose opens on a root GridVibe works out, and that one is let go after that explorer instead of inheriting the pin. A root you really did choose, with the pane still inside it, still pins exactly as before.

- **(fix) A saved workspace brings a pane back where you left it, not where it started.** Saving a workspace recorded the directory each pane was *launched* in, so a pane you had `cd`-ed somewhere else came back in the wrong place on restore — most visibly with an agent, which returned in the right mode and the wrong directory. GridVibe now records where the pane actually is. Starting an agent stamps the directory at the moment you start it, which is the last moment the shell can be asked before the agent takes over the pane. Splitting a pane opens the new one where you were working rather than where the old one started, and a pane whose connection drops reconnects into the same directory — falling back to the one it launched in if that directory has since been removed.

- **(fix) An explorer root you never chose no longer follows the pane around.** Switching a terminal to the file explorer picks a root based on where the shell is. Switching back to a terminal used to leave that root attached, so the *next* switch pinned to it — and if you had `cd`-ed somewhere else in between, the explorer opened in the old place. A root GridVibe worked out for you is now used for that one explorer and then let go, so each switch opens where the pane actually is. A root you really did choose — a Local Repository pane, or a folder you launched an explorer on — is unaffected and still pins exactly as before.

- **(feat) GridVibe follows the directory your terminal is in.** Each new terminal's prompt carries its current directory in an invisible escape sequence, which GridVibe reads out of the pane's own output. Nothing is ever typed at your prompt to ask, so unlike the old question-at-the-prompt it still answers during a build, a pager, a TUI or a running agent — and a pane running an agent reports the directory the agent was *started* in. Switching a navigated pane to the file explorer, or switching its shell, now lands where you actually are, including on agent panes, which could not be asked at all before. Local shells (cmd, PowerShell, WSL) are set up as they start, so nothing appears in the pane; SSH panes get one short line at startup, since a remote shell cannot be handed anything. An existing bash/zsh prompt hook is appended to and PowerShell's prompt is wrapped, while cmd's prompt is replaced with the default one plus the sequence. **Shell integration** in App Settings turns the whole thing off and leaves your prompt untouched.

- **(fix) Switching a terminal to the file explorer opens where the terminal is.** The explorer took the directory the pane was *launched* in and treated it as a root, so after `cd`-ing anywhere it opened above you — listing the folder you were in rather than showing it, and reporting "not inside a Git worktree" for a repository you were standing in. A pane that was never given a root no longer invents one: the explorer opens at the directory the shell is actually in, and roots on the Git repository containing it, so the sidebar works and you can still navigate up to the repository's own root. It never roots *above* the directory you picked in the launcher, and a pane you really did give a root to — a Local Repository pane, or one you have already switched out of the explorer and back — still keeps it exactly as before.

- **(fix) The explorer says when it could not tell where the terminal was.** Reading a shell's current directory only works while the shell is sitting at an idle prompt; during a build, a pager, or a slow connection it quietly fails. GridVibe used to fall back to the launch directory without a word, which is why the same click could open two different folders on two different days. When the read fails, the pane now says so and names the directory it opened on instead. A pane running an agent is no longer asked at all — the question was typed at the prompt, so on an agent pane it landed in the agent's input box.

- **(feat) Unstage All in the Git sidebar.** The **Changes** header has had a Stage All button for a while, but the only way back out was to unstage each file in turn. **Staged Changes** now carries the mirror control — a `−` in its header that empties the index in one action, disabled when nothing is staged. It touches the index only: every file on disk keeps exactly the contents it had, and Stage All puts it all straight back, so unlike Discard All beside it there is no confirmation to click through. It also works before a repository's first commit, where there is no `HEAD` to reset against.

- **(fix) Repository search no longer highlights a result you never picked.** Ctrl+Shift+F left the first line of the first file marked as the selected result the moment the results arrived, pointing at a location the pane was not showing — and it stayed marked whatever you did next. It also meant the first Enter jumped past that hit to the second one. Nothing is selected now until you click a result or step onto one with Enter or the arrow keys, and clicking a result moves the highlight to it.

- **(fix) A file stays syntax-coloured even if the background highlighter dies.** Syntax colouring for larger files is handed to a background thread, and the file shows as plain text for the moment it takes. If that thread failed, the plain text was all you got — the file you had open stayed uncoloured for as long as it stayed open, while the very next file you opened came up coloured normally. GridVibe now finishes the colouring itself when the background attempt fails, which is what it already did for anyone whose browser cannot run it at all.

- **(fix) The large-file notice says what actually made the file large.** A file is shown as plain text when it has too many lines *or* is simply too big — and a minified bundle, the case the size limit exists for, is often one enormous line. The notice reported lines regardless, so those files announced "1 lines rendered as plain text". It now reports whichever limit was reached, in lines or in megabytes.

- **(fix) The Diff view explains itself instead of coming up blank.** If the diff renderer failed to load, the Diff panel threw an error behind the scenes and left nothing on screen. It now says the view is unavailable and suggests reloading — and no longer says "No Git diff for selected file", which sent you looking for changes that were there all along.

- **(fix) Preview no longer shows a newer version of the file than Source.** Source text and the rendered Markdown preview are fetched separately, so a file edited outside GridVibe in the moment between the two could be shown half-old and half-new. The preview now checks that it describes the same version of the file as the text beside it, and waits for the two to agree.

- **(perf) Several file panes open at once no longer slow each other down.** An internal cache shared by every explorer pane only had room for one pane's work, so with three file panes open they evicted each other's — making the arrangement that needs the speed-up most the one that got none of it. It is now sized for the panes that are actually open.

- **(perf) Closing the last file explorer gives its memory and threads back.** The background threads used for syntax colouring, and the working data for the last files opened, stayed allocated for as long as the page was open, even after every explorer pane was closed. Both are now released once no explorer pane is left, and rebuilt if you open one again.

- **(fix) One background hiccup no longer disables syntax colouring for the whole session.** A single failure in the background highlighter switched it off page-wide until you reloaded, even when the failure was specific to one job. It now retries once with a fresh thread and gives up only if the problem repeats.

- **(fix) Find works again in a commit diff opened after a very large file.** A file big enough for the plain large-file view turns Find off, because that view has no per-line rows for it to point at. Clicking a commit in the Git sidebar afterwards carried that state over, even though a commit diff is not a large file — so the diff showed a Find box that marked nothing and never moved its counter, and, because the box was there, Ctrl+F kept going to it instead of falling through to the browser's own find. You had to open an ordinary file to get either back. The commit diff no longer inherits the previous file's verdict.

- **(fix) The Markdown preview is fetched once per file instead of twice.** The first time you opened Preview for a file, GridVibe asked the server for the rendered document, then immediately asked again and cancelled the first request. The cancelled one still ran to completion on the server, so every first look at a Markdown file cost two renders, and the panel flashed "Rendering preview..." twice on the way. A second request for the document already on its way now waits for it rather than starting over.

- **(fix) A search you already typed now highlights the preview when it finishes loading.** With a query in Find, switching to Preview for the first time searched the panel while it still read "Rendering preview...", so the counter said 0 of 0 and nothing was marked — and once the document arrived nothing looked again. You had to retype or step the query to see any matches. The search is now re-run over the document that actually arrives, exactly as it already was for the Diff panel.

- **(fix) The large-file view no longer drops the occasional blank line.** Very large files are painted in blocks rather than a line at a time, and a blank line landing exactly on a block boundary was swallowed by the browser as it parsed the block. The line vanished from the pane and from anything you copied out of it — a handful of times in a large log. The blocks now carry a throwaway newline for the parser to consume, so the file's own lines all survive.

- **(fix) Opening a subdirectory starts at the top again.** Browsing a long directory and stepping into a folder inside it put you at the offset you had left the parent listing at, rather than the top of the new one. GridVibe records that offset in two ways and only stopped honouring one of them when the listing changed, so the other quietly stood in for it.

- **(fix) The Diff panel comes back where you left it when you switch file tabs.** Re-opening a tab reads the file first and fetches its diff afterwards, so at the moment your position was restored GridVibe knew the file's contents but not yet its patch — and it treated not knowing as knowing it had changed, throwing the Diff scroll away every time. The Files tree and Git sidebar positions went with it, since the same false mismatch made the whole tab look stale. A position is now only discarded when the thing it points into has actually moved; a patch that has not arrived yet keeps its place until it does.

- **(fix) A big file no longer flashes back to its start when it is re-read underneath you.** A file large enough to be painted over several frames used to have its rows taken away before the first new ones landed, which put you at line 1 for the whole rebuild and snapped you home at the end — a log file gaining a line did that on every poll, and a save did it once per file. Worse, the browser reports that reset as a scroll of your own a moment later, and GridVibe believed it, so the position it was about to restore was overwritten by the rebuild's own doing and the file stayed at the top. Rebuilds are now assembled off-screen and swapped in complete, so what you were reading stays put the whole time, and a reset that the rebuild caused is no longer mistaken for one you asked for.

- **(fix) Find no longer follows you from one file tab to the next.** Typing a query in one tab left it on the pane, so opening another tab searched the incoming file with a query you had not typed there — marks over its text, a counter you did not ask for, and a jump to that query's first hit that landed on top of the position the tab had just restored. The query now belongs to the tab and to the file it was typed against: a pinned tab keeps its own find, the Preview tab drops it when a different file loads into it, and re-opening the same file gets it back. Rebuilding a file's rows also stopped counting as a reason to move you — the restore of where you were is the only thing that decides that now.

- **(fix) Clicking a changed file in the Git sidebar no longer fetches its diff twice.** Every click issued two identical requests, one of them cancelled a moment later, and ran `git diff` twice on the server for a patch already on its way. Two independent paths asked for the same patch inside one frame; the second now joins the first instead of superseding it. A request for a genuinely different diff still supersedes, as before.

- **(fix) A large file interrupted mid-render no longer leaves the pane unable to restore anything.** Rows for a big file arrive over several frames; if the panel they were filling was replaced before the last one landed — by opening the in-place editor, by the reduced view taking over, by a tab switch — the unfinished build was never closed out, and everything waiting on "the rows are ready" waited forever. Scroll restores, the selection carried out of edit mode and the Git sidebar's active-row highlight all quietly stopped working in that pane until the next full re-render. Such a build now stands down and releases what was waiting on it, and opening the editor closes it explicitly rather than leaving it to notice a frame later.

- **(perf) Switching session groups with a large file open no longer stutters.** Leaving a group re-hashed every open file from the first character to the last, once per explorer pane and again on the way back, purely to notice that nothing had changed — about 58 ms per 10 MiB pane, per switch, in each direction. That answer is now kept until the bytes actually move. The incoming group's file listing and its three sidebar panels are also put back in one measuring pass and one writing pass instead of four interleaved rounds, and they stop as soon as they have landed rather than running a fixed number of times. And a large file still filling in line by line is paused while its card is off screen, resuming exactly where it stopped when you come back, so it is no longer competing for frames with the group you actually switched to.

- **(fix) The viewer's right edge no longer moves between Source, Preview, Diff and edit mode.** Opening a file for editing, opening an empty file, or opening one large enough for the reduced view all stood the Source overview column down — and because that column's lane collapsed with it, the text beside it widened by the column's width, re-wrapped every line, and slid the scrollbar sideways; leaving edit mode did the whole thing again in reverse. The lane is now reserved whether or not the column has anything to show, and the column stands down in place: it keeps its strip and its separator and gives up only its markers, its viewport box and its gestures. Markdown Preview and the Diff view reserve the same lane, so switching between the three no longer moves the scrollbar or changes the measure the text wraps to. All three views also keep space for their scrollbar permanently, so a fold, a Find that changes which lines are shown, or a switch into the reduced view no longer reflows the text just by making the bar appear or disappear.

- **(fix) Markdown Preview now returns to the place you left it.** Preview content is rendered lazily, but its saved scroll was being applied when the unrelated Source rows finished — usually before the Preview HTML existed — so switching tabs, switching Source/Preview views, saving or refreshing a Markdown file, and switching session groups could all return the panel to the top. Scroll is now kept and revision-checked per panel, so a Diff revision that has not arrived during a tab render cannot discard a still-valid Preview offset. The visible panel is restored when its own content can hold the offset; Preview reapplies on render arrival, with one guarded correction if a lazy Mermaid diagram above it changes the document height. Retries are animation-frame bounded, a reader who scrolls cancels any later correction, and a response for a file or panel that has already been replaced cannot move the new one. Source keeps its existing source-render queue and Diff keeps its async arrival path.

- **(fix) Two scroll positions that would not stay put.** **Leaving a Preview tab and coming back threw you to the top** of a long Markdown document. Every route into the Preview panel — selecting its tab, switching between Source, Preview and Diff, and every keystroke in Find — rebuilt the whole panel from scratch, which puts the reader at the top by definition; and since diagrams are now drawn as you scroll to them, the freshly rebuilt panel is also *shorter* than the one it replaced, so the restore that follows had no way back either. A panel already showing the current render is now left alone, so it keeps both your place and the diagrams that have already drawn. **And scrolling sideways in a large file felt like it was fighting back**, pulling the view a little further in than where you left it. The horizontal position was being restored as a *fraction* of the longest line in the file rather than as the column you were actually on — and the longest line changes: a folded section, or a row a progressive render has not emitted yet, is enough. A restore now returns the exact position whenever it has one, and falls back to the proportional one only for a workspace restored after a restart, which is the only case that has nothing else to go on.

- **(fix) Large files: the freeze the last round moved rather than removed.** Manual testing found the previous two changes had shifted the cost around instead of getting rid of it, in four separate places. **Typing in Find still lagged behind the keyboard.** The repaint that was supposed to rewrite only the lines whose highlight moved gave up and rebuilt the whole document whenever more than 400 lines were affected — which is the first two characters of almost any query on a large file, so every one of those keystrokes rebuilt tens of thousands of lines and threw away your scroll position and your selection with them. The limit now scales with the file, because what it is being weighed against is the cost of rebuilding *that* file. Two other costs went with it: the lines to repaint were being located one search of the whole document at a time (a thousand of them in a twenty-thousand-line file meant twenty million nodes walked to rewrite a thousand), and the document was being re-derived from scratch three times per keystroke. **Every large file was still being built twice on open**, because the second render — the one that draws the search marks — counted a build that was still in progress as a reason to start again even when it had nothing to add. **The colouring froze the window when it arrived.** Moving Highlight.js to a background worker took the parsing off the main thread but left the unpacking on it: the answer for a 300 KB file is well over a hundred thousand pieces, and all of them were being built in one go the moment it came back. They are now built a line at a time, as the lines are drawn. **And the paint itself could still overrun**, because a frame was measured in lines rather than in time — 2,000 lines of a minified bundle and 2,000 lines of a config file are nothing like the same amount of work. A frame now ends when its time is up, which is what makes "fills in from the top" actually mean the window still answers clicks while it does. The same budget now paces the **large file view**'s plain blocks, which were being escaped and inserted all at once, and those blocks are bounded by size as well as by line count — the 4 MiB ceiling exists for the file that is one gigantic minified line, and that file has no line breaks to cut at, so it was being handed back whole. **Your scroll position now survives the colouring.** A large file would open, restore where you were, and then jump back to the top a moment later when the syntax colours landed and the lines were rebuilt underneath you; a rebuild of the same file now keeps the offset across it.

- **(feat) Very large files now open instead of hanging the window.** Opening a big log or a generated file used to lock GridVibe up for seconds — tabs would not switch, terminals stopped painting, clicks queued. The reason was that the viewer built one row of HTML per line of the file: a 200,000-line log is well over half a million elements, laid out and styled before anything appeared. Past 20,000 lines, or 4 MiB, a file now opens in a **large file view**: the text is rendered as bounded plain blocks instead of per-line rows, and it appears in well under a second. There is a real trade and the pane states it in a notice at the top, which names every part of it: no syntax colouring, no line numbers, no section folding, no change marks in the gutter and no overview ruler down the side. **Find is unavailable in this view**, and the notice says so in those words rather than leaving you a search box that quietly does nothing — the find is built on the per-line rows this view does not create, and the only other way to search it would walk the whole 10 MiB buffer, which is the freeze the view exists to remove. Download and Edit still work, and the in-place editor drops to a plain text box exactly as it already did above 2 MiB. Files below the threshold are untouched and look and behave exactly as before — the biggest file in GridVibe's own source is about 8,000 lines, so this is aimed at the generated and logged files that were never really openable in the first place.
- **(feat) Very large diffs open too, and tell you what they gave up.** A big diff ran word-level line matching, character-level intraline comparison and syntax highlighting over the whole patch before drawing anything, all on the one thread the rest of the app runs on. Diffs now come in three sizes. Small ones — the overwhelming majority — are exactly as before. Medium ones keep the side-by-side layout, the line numbers and the undo buttons, and give up the character-level emphasis inside a changed line and the syntax colour. Very large ones are drawn by GridVibe's own side-by-side renderer instead of the vendored one, which costs the remaining styling and nothing else. In every case a banner names the size so the missing colour reads as a decision rather than a bug, and in every case **the per-line and per-block undo buttons are still there** — that was the deciding constraint, since a plain-text rendering would have been simpler and would have removed the one thing that can actually change a file from precisely the diffs where you most want it. A diff that hits the existing 256 KB / 4,000-line ceiling is still marked truncated as before.
- **(perf) Opening a file, and clicking through several, got noticeably lighter.** Four unrelated costs, none of them visible as a feature: **Markdown is no longer rendered until you look at it.** Every open of a Markdown file — and every save — rendered and sanitized the whole preview on the server and then, in the browser, inserted it, re-highlighted every code block and drew every Mermaid diagram one after another, whether or not you ever left the Source view. A README with a dozen diagrams could freeze the pane for seconds on open. The preview is now fetched and drawn the first time you select the **Preview** tab, so opening in Source is fast and the pause lands once, on the tab that needs it; later visits are instant, and diagrams below the fold now draw as you scroll to them rather than all up front. **Clicking quickly through files stops backing up work** — a file, diff or gutter-mark request that a newer click has already replaced is now cancelled instead of running to completion for something nobody is looking at. **The gutter's change marks ask for a smaller diff**: they need only the added and removed lines, so they no longer request the six lines of surrounding context per change that were being sent and parsed and thrown away. **And a wrapped diff stopped stuttering** while lining its two sides up: the pass that equalises the row heights now measures every row before it resizes any of them, instead of forcing the browser to redo its layout once per pair of rows. None of this changes what you see — the same marks, the same alignment, the same preview.

- **(perf) Finding, typing and opening in a large file stopped rebuilding the whole document.** The Source view used to throw away every rendered line and build them all again on almost any interaction: each keystroke in **Find**, each press of Enter to step to the next match, each Markdown section you folded, each time you entered or left the in-place editor — and twice over on every single file open, because the pane rendered its lines and then rendered them again to mark the search. On a few thousand lines that is a stutter; on a few tens of thousands it is a freeze. Now a repaint is a repaint. Stepping from one match to the next rewrites exactly the two lines whose highlight moved and leaves every other line alone; a render that would draw what is already on screen draws nothing at all, which is the second half of every file open gone. Two things you may notice as a result: **your text selection and the matching-word tint stop disappearing** every time you type in Find or fold a section, because the lines they are anchored to are no longer destroyed under them. Only a real change — different content, a different language, a different set of folds — rebuilds. **Typing in the in-place editor** on a large file was the same problem from the other end: the coloured text behind the caret was re-parsed and re-emitted in full on every animation frame, so the cost of one keystroke was the size of the file rather than the size of the edit. It now replaces the line (or the handful of lines) you actually moved, and repaints the whole buffer with full syntax colouring a fraction of a second after you stop typing. The visible trade is small and brief: the line under the caret is coloured by the simpler built-in highlighter while you are typing, and settles to the full colouring when you pause. **And a file big enough to be slow now fills in from the top** — above roughly 4,000 lines the pane paints in frame-sized batches while the rest of GridVibe stays responsive, instead of the window locking up and then showing everything at once. The jump to a find match and the restored scroll position land a beat later than they used to, once the lines they point at exist. Files below that stay exactly as instant as they were.
- **(perf) Syntax parsing and the largest Diff parse no longer take the window's only UI thread.** Highlight.js now runs in one lazy worker pool shared by every explorer pane once a Source buffer is large enough for worker startup to be worthwhile (64 KiB); smaller files keep the old synchronous path. The text paints first as readable plain rows, then gains its full syntax colour when the worker answers, and the in-place editor's settled underlay uses the same route after typing pauses. The result is transferred as compact typed offset/length/class arrays rather than a giant cloned tree of JavaScript objects. The already-degraded **large Diff** tier sends its handwritten side-by-side parse through the same pool, shows its tier notice and a short rendering state meanwhile, then wires the same per-line and per-block undo controls onto the rows. The pool leaves one logical processor for the browser, never grows past four workers, and kills a running job when a newer file or draft supersedes it; identity is checked again before paint, so an old answer cannot flash over the file you clicked next. Everything is still self-hosted: the worker imports GridVibe's existing pinned Highlight.js file from `/static/vendor`, with no CDN and no frontend build step.

Matching ignores case, and the box stays put at the top of the section while you step, so the counter is still readable once the scrolling starts. The sidebar is narrow, so the box is folded away until you ask for it and gives its row back to the commits when you are done. One thing worth knowing about the highlight: a commit subject that is too long for the sidebar gets cut off, and a match past the cut is a highlight nobody can see — so every commit with a hit also tints its short hash, which is always visible at the left edge of the row, and tints it brighter for the hit you are currently on. That way scrolling the graph shows you where the matches are even when the matched word itself is off the end of the line. The search covers the commits the graph has loaded, which is the same set the rows show; it reads what is already on screen and makes no request, so it costs nothing and works the same on a remote pane as a local one. - **(fix) The Git sidebar now shows you which diff you are looking at — and a restored workspace no longer hides it inside a closed commit.** Open an old commit in the Git graph, click one of its files, and the diff appears in the viewer — but nothing in the sidebar said so. The row you clicked looked exactly like the other three rows naming that same file (Staged Changes, Changes, and the row inside every other commit that touched it), so on a file with any history there was no way to tell which version was on screen. That row is now marked, and so is the commit it belongs to. The mark follows what the viewer is actually showing rather than the path alone: a commit's row lights up only for *its* commit, a Staged row only while the staged diff is up, and none of them while you are looking at a directory listing — which is the whole point, since four highlighted rows for one file would say no more than none. **Restoring a workspace used to make this worse.** The Git graph came back with every commit collapsed, so a restored commit diff was sitting in the viewer with nothing anywhere naming it — you could see a patch and could not tell which commit, or even which file, it came from. Two things caused that. The commit that owns the open diff is now opened and scrolled to when the sidebar loads, once, so the restored diff always has a row pointing at it; collapse it and it stays collapsed, and no later refresh reopens it behind your back. And the expansion itself was being thrown away on the way out: for any session tab that was not the one on screen when the workspace was saved, GridVibe recorded the pane's expanded commits — and its expanded tree folders, its sidebar width, and its scroll position — as empty rather than reading them off the pane. Background tabs now come back the way you left them, the same as the visible one always did.

- **(fix) A pane whose TUI crashed no longer types mouse gibberish at the prompt — and **Reset view** is now the button that fixes it.** Kill an `opencode`, a `vim`, or anything else full-screen without letting it shut down properly — a crash, a `kill -9`, an SSH connection that drops — and the pane was left in a state you could not type in. Every movement of the pointer over it filled the command line with `35;43;24M35;43;19M35;39;18M…`, and one absent-minded Enter submitted the lot. The cause is not GridVibe's doing: mouse reporting belongs to whatever runs in the pane, which switches it on when it starts and off when it exits, and a program that dies mid-flight never sends the "off". The shell that gets the prompt back has no interest in mouse reports and dutifully types every one of them. What *was* GridVibe's doing is that the two buttons in the pane header which look like they should fix this disagreed about it. **Clear** worked; **Reset view** did not, and the reason was invisible: both reset the pane, but Reset view then re-syncs it from the short buffer of recent output the server keeps — and the dead program's "mouse on" is still sitting in that buffer, so it was re-delivered a moment after the reset that had just cleared it. It was, in effect, resetting the pane and then undoing it. Both buttons now switch mouse reporting off explicitly, and Reset view waits for the replayed output to land before it does — so it cures the pane instead of restoring it to exactly the state you were trying to escape. Nothing is sent to the shell to do this; the fix is entirely in the pane, so there is no stray command at your prompt and no output you did not ask for. **The buffer itself is untouched, on purpose.** The same replay is what brings a pane back after a reload or a switch between session tabs, and a pane with a TUI still running in it needs that program's mouse reporting restored with it — filtering the buffer would have broken the working case to fix the broken one. The trade is that Reset view is now genuinely a reset: a full-screen program still running in the pane loses its mouse support until it turns it back on, the same as pressing Reset in any terminal. The pane this exists to rescue has nothing left running to turn anything back on.
- **(fix) A file explorer pane now opens any text file, not just the ones on a list of names.** `Dockerfile_chss` refused to open at all — "Explorer file format is not supported for editor preview" — and so did `Dockerfile.dev`, `Jenkinsfile`, `LICENSE`, `VERSION`, a Terraform `.tf`, a systemd `.service`, and every extensionless script in a `deploy/` folder. The pane was deciding what it could show from the **filename alone**, against a fixed list of extensions plus a handful of exact names, and that list matched `Dockerfile` exactly — so the moment a project appended anything to it, one of the most-edited files in the repository became unopenable. The decision now belongs to the file's **contents**, which is the check that was already there and was never reached: a name the pane recognises still picks the syntax colours, and a name it does not is opened as plain text if it reads as text, refused only if it is actually binary. The refusal is bounded the same way it always was — a few kilobytes are sampled to decide, so an unrecognised binary is turned away without first being read whole over SFTP. The Docker and Make families are recognised by name now rather than by exact match (`Dockerfile_chss`, `Dockerfile.dev`, `api.dockerfile`, `Makefile.local`, `build.mk`), so those keep their highlighting instead of falling back to plain text. **Nothing about the explorer's read-only contract moved**: this changes which files are legible, not what may be done to them. Files that now open are also editable in place, on exactly the same terms as every other text file — root-confined, 10 MiB, complete UTF-8, one line-ending style, and the revision check that refuses a save if the file changed underneath you — and a file whose contents are binary is still refused on the way in and on the way out.
- **(fix) A file explorer pane can no longer be hung or ballooned by the repository it is pointed at.** Every Git command an explorer pane runs — the branch badge, the Git sidebar, the commit graph, a diff, staging, committing, pushing — now has a ceiling on how much it may return and a hard limit on how long it may take, and neither depends on the call site remembering to ask. Three things were wrong. **Output had no bound unless a caller supplied one**, and only repository search ever did: a `git status` or a `git diff` in a very large repository was read into memory whole, and the Diff view then threw away everything past 256 KB — after paying for all of it. Both streams are now read up to a limit and stopped there, so the memory cost is GridVibe's to set rather than the repository's; the Diff view reads 256 KB and one byte, which is all it takes to know there was more. A truncated view is marked truncated exactly as before. **A read could stop on a password prompt nobody can answer.** Commands that change something already suppressed the prompt; commands that only look were the ones that did not, even though `git status` consults the tracking branch and can reach the network to do it. Against a host that wants credentials — a token that expired, a repository moved behind auth — the pane just stopped, with the request thread parked on a prompt on a machine with no terminal attached to answer it. Every command suppresses the prompt now, and fails cleanly with the reason instead. **And the timeout did not cover git's helpers.** Git hands its output pipes to separate transport programs it starts for network work, so killing git alone leaves one of those holding the pipe open and the "2 second" timeout waiting on it — the same defect that once turned a 30 second bound on the updater into a four and a half minute wait. Explorer commands now start in their own process group and take the whole group down together, with a second bound on the cleanup, so a stalled remote gives the pane back on time. The same for a remote pane over SSH: both channels are read to a limit against a deadline, and a command that goes quiet is closed rather than waited on. Nothing about what the panes show changed, and the one internal caller that already had a tighter limit — repository search, 8 MB — keeps it.
- **(fix) A file explorer pane now opens on its folder instead of an empty viewer.** Launching or importing a session with Explorer selected left the pane on "Select a file to view", with the path bar showing the plain text of the directory it was launched with — not the clickable trail, because that only gets drawn when a directory is actually loaded. Both fixed themselves the moment you clicked a folder in the tree and walked back up to the top, which is exactly where the pane should have started. It now starts there: a pane with nothing saved to restore browses its explorer root straight away, so the first thing you see is the root listing with a live breadcrumb and the branch badge beside it. Nothing else about the restore changed — a saved file or a saved directory still wins the Preview tab, and a restored pinned tab still keeps the viewer. What that last case gained is the same fix one step later: the Preview tab now knows it means the root, so switching to it shows the listing rather than the empty state.
- **(fix) Browser mode now starts in its own browser window, and a restore that cannot open a tab says so.** Two halves of the same complaint: starting GridVibe dropped the launcher into whatever browser window happened to be in front — wedged between your mail and everything else you had open — and restoring several workspaces at once brought back only one of them. The first is now fixed outright. Browser mode is **one browser window per run**: GridVibe asks your default browser for a new window rather than a new tab, so the launcher and the tab each workspace opens live together in a window of their own. `webbrowser.open(url, new=1)` is the obvious way to ask for that and it does not work on Windows, where the URL goes to the shell and lands in the frontmost window regardless — so the default browser is looked up and started with its own new-window flag (`--new-window` for the Chrome/Edge family, `-new-window` for the Firefox one). A browser we do not recognise, or one that will not start, still opens exactly as before; nothing about which browser you use changed. The second half is not a bug in GridVibe, and pretending otherwise was: **the restore was asking for every workspace's tab all along, and the browser was refusing.** A page may open exactly *one* tab per click — the first `window.open` consumes the click's authority and every later one in the same click comes back empty — so a restore of four workspaces gets one tab and three refusals. GridVibe never looked at the refusals, so the other three simply never appeared, with nothing said and their sessions running perfectly well in the background. Restore now counts them and reports once on the banner: "Relaunch started for 4 workspaces. Your browser blocked 3 workspace tabs. Allow pop-ups for this site so GridVibe can open workspace tabs. You can also open them from the Workspaces list." Both ways out are real. Allowing pop-ups for GridVibe's address is a one-time setting after which every restore opens every tab; the **Workspaces** card lists each restored workspace with its own **Open** button, and a click of your own is authority the browser always honours. The same reporting now covers every other place a tab is asked for — the launcher's Open button, `Alt+W` back to a workspace, and the session window's own workspace switches, which report on the session toast — so a refused tab is never again a window that just does not change. Nothing about what gets restored moved: the sessions relaunch server-side exactly as before, in one transaction, whether or not their tabs open.
- **(fix) Going back to the launcher in browser mode no longer opens the restore dialog every time.** Pressing ``Alt+` `` or the launcher button at the head of the session tab line threw up the "reopen saved workspaces" chooser on *every* trip, and it was almost always a dialog with nothing in it to do: the one row it listed was the workspace you had just left, marked already open and therefore un-restorable. The native window never did this, which made it look like a browser quirk. It was not — it was the two modes reaching the launcher by different routes. The native launcher is a real window that gets *focused*, so the startup check that makes the offer runs once per run of the app. Browser mode has no such window: the same keystroke and the same button **navigate**, which reloads the launcher page and re-runs everything it does on load, including the offer. The check now asks the question the offer was always about. Restoring a workspace exists because a restart ends every live shell, so the snapshot is the only way back — which means the offer belongs on a GridVibe that has come back **empty**. If anything is running, the chooser no longer opens itself, in either mode, and hopping to the launcher and back is silent. The single-workspace banner has always worked this way (it refuses to offer while the workspace has live tabs); the chooser now asks the same question across every workspace instead of only about the row in front of it. Nothing is hidden: **Reopen saved …** in the Workspaces card still opens the chooser whenever you want it, the list behind it is still refreshed on every launcher load so it is never stale, and a genuinely fresh start after a restart still offers on its own exactly as before.
- **(fix) Saving an App Setting can no longer leave a page reading half of the old one.** GridVibe re-reads its settings after every App Settings save, and it used to install the new values one at a time — the theme, then the terminal font, then the session limit, then the voice model. A page that loaded during that fraction of a second, or a workspace that asked for its settings just then, could be answered with a mixture: the new theme beside the old font, a combination no settings file ever contained. Settings are now swapped in as one complete set, and anything that reads several at once takes a single copy to read from, so a request is answered entirely from before the save or entirely from after it.
- **(fix) Two windows can no longer create the same workspace name at the same moment.** A workspace name belongs to one workspace: the launcher refuses a name another live or saved workspace already holds, so opening "api work" always means the same thing. That refusal was a look rather than a reservation — two launcher windows submitting the same name at once, a create racing a rename, or two launches into a new workspace of that name, could all be told it was free and all take it, leaving duplicates in the picker that no later rename could tell apart. Taking a name is now one indivisible step: one request gets the workspace and the other gets exactly the refusal it would have got a second later. Unnamed workspaces are unaffected — an empty name is not a name, and any number can be created at once.
- **(fix) A remote explorer pane no longer fails a click because its connection was hung up a moment before it was used.** Explorer panes over SSH share one connection per session, and a connection nobody is using gets hung up after a minute. 1.9.0 fixed the obvious half of that — a long download or search *holding* the connection is no longer counted as idle — but a request does not simply take the connection and go: it takes the connection and then opens its own private channel on it, which is a round trip to the server. Until that channel came back, the request did not count as holding anything, so for the length of the round trip the connection looked unused to everything else on the page. The check that hangs up idle connections runs whenever any request in the pane starts, so a connection picked up at 59 seconds of that minute could be closed by the very next click — and the request that had just chosen it failed with a connection error, on a pane where nothing was wrong and nothing you did caused it. It was rare by construction and it was pure bad luck when it happened. The connection is now claimed at the moment it is chosen, *before* the channel is opened, so the gap no longer exists; the claim is released as soon as the request finishes, exactly as before. The claim also belongs to the specific connection it was made against rather than to the pane, which matters in the one case that looks similar and is not: if that connection is torn down while the channel is opening — you closed the session, or it dropped — and a new one takes its place, the request finishes on its own handle and closes it, instead of pinning a connection it never used and leaving it un-hangupable for the rest of the run. Nothing about the one-minute timeout, the sharing itself, or what happens to genuinely idle connections has changed, and no network work happens while the pane's connections are locked.
- **(fix) Your settings file is now as hard to lose as your saved sessions.** GridVibe keeps three files on disk that matter: your saved launcher presets, your workspace snapshots, and `config.json` — the settings you change from App Settings. The first two have been written carefully for a while: locked so a second copy of GridVibe cannot silently overwrite the first, flushed to disk before the swap so a power cut cannot truncate them, backed up before every change, and set aside rather than discarded if they ever come back unreadable. `config.json` had none of that. It got the simplest possible write, and if it ever came back corrupt — a truncated file after a crash, a bad hand-edit — GridVibe quietly fell back to defaults and the next thing you changed in App Settings wrote those defaults over the top. Your theme, your font, your SSH policy, your search limits: gone, and nothing said so. It now uses exactly the same machinery as the other two. A corrupt settings file is kept aside as `config.json.corrupt-<timestamp>` instead of being overwritten, and your previous settings are recovered from the backup automatically. If a save genuinely cannot reach the disk — a full disk, a permissions problem, an antivirus lock — App Settings now tells you it failed instead of showing you the new values as though they had been saved. One deliberate difference from the other two files: if GridVibe merely *cannot open* `config.json` right now (something else is holding it), it recovers from the backup for that read but leaves your file exactly where it is, because a file it could not read is not the same as a file that is broken.
- **(perf) Downloading a large file no longer holds it in GridVibe's memory.** Downloading a 90 MB file from an explorer pane used to read the whole thing into memory before sending you a single byte of it. It worked, and on a remote pane over SFTP it meant a visible pause with nothing happening, plus 90 MB of the app's memory tied up for the duration. The file is now read and sent in small pieces as it goes, so the transfer starts immediately and the memory cost is a fixed handful of kilobytes no matter how big the file is. Nothing about what you are allowed to download changed: the path is still confined to the pane's root, the 100 MB ceiling still applies and is still checked before the download starts — so a file over the limit still refuses cleanly rather than starting and stopping halfway — and a file that grows while it is being sent still stops at the size GridVibe announced. Pausing and resuming a download still works — the browser asks for the rest of the file by byte offset and gets it. On a remote pane, the SSH connection is returned to the pool when the transfer finishes, including when you cancel it midway.

- **(fix) A download that fails now says so, and a batch of them says it once.** Downloading a file from an explorer pane in the browser worked by building an invisible link and clicking it. That is the standard trick, and it has one property nobody notices until it matters: the page never learns what came back. A row the tree drew before the file was deleted elsewhere, a path the server refuses, a file over the 100 MB download ceiling — all three answered with an error the click could not see, so all three produced the same green "Downloading…" message and no file. You went looking in your downloads folder for something that was never sent. Multi-entry selection made that worse in proportion: select nine stale rows and you got nine green messages in a row and an empty folder. The native window never had this problem — it routes downloads through a real save dialog and reports what actually happened — so the two halves of the same feature disagreed about whether downloads can fail. The browser path now fetches the file first and only then hands it to the browser to save, which means the response is a thing the page can read: a failure reports as a failure, in red, carrying the reason the server gave ("File not found" rather than a status code, where the server names one). A selection of several files reports **once** for the whole batch — "Downloaded 7 of 9 files — 2 failed: …" — instead of one message per file, matching how the explorer's other multi-entry actions already report. **Large files still stream rather than being held in memory.** Reading a response before saving it means holding it, which is fine for source files and not fine for a 90 MB archive, so anything above 25 MB is handed straight to the browser to stream to disk exactly as before — but *after* the status has been checked, so the failure cases above are already ruled out by the time that happens. The size ceiling, the root confinement, and the read-only contract are all untouched: this changes what the page is told, not what it may ask for.

- **(polish) The last four `+`/`−` text buttons in the explorer became icons.** The Git sidebar's stage and unstage buttons, its stage-all button, and the editor's font-size pair drew their symbols as text characters while every control beside them — revert, open folder, download, appearance, line wrap — was a drawn icon. - **(fix) Checking for updates can no longer hang forever, and one click can no longer cost a worker thread.** **Check for updates** runs half a dozen git commands inside the request that serves it, one of which — `git fetch` — talks to whatever remote your checkout tracks. None of them had a time limit, and none of them told git that there is nobody here to answer a question. Those two gaps compound into the same outcome. A private remote over HTTPS with no cached credential makes git stop and *prompt* for a username, on a server that has no terminal to prompt into, so it waits for an answer that cannot arrive; a remote that is unreachable rather than unfriendly — a VPN that dropped, a host that accepts the connection and then says nothing — simply never returns. Either way the button spun indefinitely, `/api/app-update` never answered, and because the launcher's request has no timeout of its own and the button offers no cancel, the only visible option was to click it again — which started a second one. Each attempt permanently parked a worker thread. Every git command in the update flow is now bounded twice over: `GIT_TERMINAL_PROMPT=0`, so a remote that wants credentials **fails** instead of waiting (this is the rule the explorer's Git sidebar has always followed for its own writes; the updater was the one caller that did not), and a timeout — 30 seconds for the two commands that use the network, `fetch` and the fast-forward `pull`, and 10 for the local ones that only read the checkout. A command that runs out of time reports through the same banner as any other update failure, naming the timeout and the two things that cause it, so a stalled update now looks like a failed update rather than like nothing happening at all. **The timeout also had to kill more than git itself to be worth anything.** A first attempt bounded the wait and was measured, against a remote that accepted the connection and then went quiet, reporting its 30-second timeout after **269 seconds** — because `git fetch` hands its output pipes to the helper processes it spawns, and killing the one process we launched leaves a helper holding the other end. Reading stops when the pipe closes, not when the process we know about dies, so the wait continued until git gave up of its own accord: the bound was being enforced against the wrong thing. Timed-out commands are now killed as a process *group*, and the tidy-up after the kill is itself bounded, so the same case now returns in 30.2 seconds and leaves nothing running behind it. Nothing about a working update changed: the happy path spends no longer than it did, and a fetch against a reachable remote is not remotely close to 30 seconds. Note that this bounds *GridVibe's* wait, not git's own credential helpers — a desktop helper that opens its own window is outside the process, and the timeout is what covers that case.
- **(fix) `logs/gridvibe.log` is readable again — 84 % of it was paramiko.** Explorer panes over SSH share one pooled connection but deliberately open a fresh SFTP channel per request, because paramiko's SFTP clients are not safe to use concurrently and a channel on a live connection is cheap. That design is right and is not changing. What nobody had done is turn off paramiko's running commentary about it: two `INFO` lines per channel, *"Opened sftp connection"* and *"sftp session closed"*, at whatever rate you happen to be clicking. On a measured hour of ordinary use that was channel number 2,298, about a hundred lines a minute, and **84 % of every line in the file**. The consequence is not noise for its own sake — it is retention. The log rotates at 2 MB and keeps ten of them, and a full rotation was down to roughly **300 GridVibe lines**, so the entire 22 MB budget held a few hours of diagnostics where it used to hold a hundred times that. Anything you actually wanted to look up had already been pushed out by bookkeeping about SFTP channels. paramiko is now muted to `WARNING` outside debug mode, which is where it logs the things worth reading: authentication failures, transport errors, host-key problems. Those are unaffected. `python main.py --debug` restores the full stream, so diagnosing an SSH problem still has the detail available on request — it is one flag rather than a code change. Filtering individual records was considered and rejected: when an entire level is per-operation bookkeeping, the level is the right instrument.

The reason was invisible from the outside: a text box keeps its selection to itself, so the shortcut, which reads the page's selection, saw nothing there to seed with. An editor now answers for its own pane, so the gesture behaves identically on both sides, and it opens on the match **under the word you picked** rather than at the top of the file, exactly as it does when you are only reading.
- **(fix) The selected-word tint is readable on a dark explorer pane.** Double-clicking a word tints its other occurrences, and on a dark pane that tint was set *weaker* than on a light one — the opposite of what a translucent wash needs, since the same amount of colour separates far less from near-black than it does from white. It was easy to miss entirely. It is now the stronger of the two, in the Source view and the in-place editor alike, with the editor's own selection raised alongside it so the word you actually picked still reads as the anchor the rest hang off. Light panes are unchanged.
- **(feat) Find now works while you are editing a file, and the selected word lights up its other occurrences again.** Both were casualties of edit mode rather than decisions: the find box was greyed out the moment you clicked **Edit**, and double-clicking a word stopped tinting the rest of them, because the panel held a plain text box with nothing in it to mark. Now that the rendered rows stay on screen behind what you are typing into, both are back, and both search **the draft in front of you** rather than the file as it was on disk — so a word you just typed is findable, and a line you just deleted is not. The find box, the `1/12` counter, `Enter` and `Shift+Enter`, the up/down buttons and `Escape` all behave exactly as they do when you are only reading. Stepping between matches is noticeably quicker than in the read-only view, because moving the highlight no longer rebuilds the document to do it. Two details are deliberate. The match you are standing on is marked by **colour alone** rather than the thin outline the read-only view draws around it — an outline is a shape, and shapes are exactly what the layer behind your text is not allowed to have, or the two would stop lining up. And finding a match **does not move your cursor**: `Enter` takes your eyes there, not your insertion point, so a buffer with unsaved changes never quietly relocates where the next character will land. Selecting a word tints every other occurrence of it, skipping the one you selected, whole-word for plain identifiers so double-clicking `id` does not light up every `width`, and it clears when you click away. **The selected word survives clicking Edit and clicking Cancel**, in both directions, so a word you picked while reading is still picked — and still lit — once you are editing, and still there when you come back out; it used to go dark at each swap and have to be selected again on the other side. What crosses is the word itself rather than a position in the file, so a discarded draft cannot hand the highlight to whatever now happens to sit at those coordinates: if the word is no longer on that line, nothing comes back rather than the wrong thing. On a very large file — the same size at which the coloured rows already step aside — the find box stays greyed out as before, because with no rows behind the text there is nothing to mark, and browsers without the underlying paint feature simply see the older behaviour. Nothing about editing, saving, the conflict flow or the unsaved-changes prompts is touched, and the change bars in the gutter still stay stood down while you edit.
- **(fix) Saving a file no longer throws you back to the top of it, or to the top of the file tree.** Save captured your place in the document and then, on the save most likely to happen mid-file, dropped it: a file that matched its last commit gains a Diff panel the moment your edit makes it differ, and that new panel sent the refresh down a full-rebuild path which was never handed the position that had just been captured. So the first save of a clean file always came back at line one. It now lands exactly where you left it, on every save. The file tree beside it was a separate injury with the same cause — a save discarded every folder the tree had loaded and re-read each expanded one, flashing a near-empty panel, spending a request per folder, and scrolling back to the top of a tree you had navigated by hand. A save changes a file's *contents*; it cannot create, delete or rename anything, so the only row that can have moved is the saved file's own. Just that one directory is re-read now, its rows stay on screen while it happens, and every other folder keeps its contents, its expansion and the panel's scroll position. A folder being re-read no longer replaces itself with **Loading…** either — that placeholder is now only for a folder that has nothing to show yet.
- **(opt) Editing a file in place no longer throws the page away and starts again.** Clicking **Edit** replaced the rendered Source view — numbered rows, syntax colours, the lot — with a bare text box in a single frame, and the jolt was as much geometry as colour: the line-number gutter vanished, so every glyph in the file jumped left by the width of the gutter and down by the text box's own padding, and you had to find your place again in a document that had just shifted under you. The rendered rows now stay where they are and the editing surface sits **on top of** them, transparent, so the gutter survives the whole edit and not one character moves on the way in or on the way back out. Your scroll position survives with it, in both directions, because the panel that scrolls is now the same panel in both modes rather than a second scroller handed the position on each switch. Everything about editing itself is unchanged: the same text box does the typing, so `Tab`, `Ctrl+S`, `Escape`, dictation, the line-wrap toggle, zoom, the source-font picker, the conflict flow and every unsaved-changes prompt behave exactly as they did, and what gets saved is byte-for-byte what it was. **The syntax colours stay on while you type**, and they are the read-only view's own colours rather than a second highlighter's approximation of them, because the layer you are reading *is* the rendered Source view — it simply keeps up with your draft instead of the file on disk. Selecting text tints the lines rather than blanking them, so the colours stay legible under the selection. Markdown headings keep their colour too, though their fold arrows are gone for the duration of an edit: they would sit under the editing surface with no way to click them, and folding a file you are typing into makes little sense anyway. The change bars in the gutter and the overview ruler stay stood down for the duration of an edit, as before: they describe the file as committed versus the file on disk, and a draft you have not saved is neither. On a very large file the overlay quietly steps aside and edit mode looks exactly as it always did, with no message about it, because it is an enhancement and never a condition of being able to edit.
- **(fix) Line numbers past 999 no longer nudge the code sideways.** Every row in the Source view sized its own number gutter, which agreed with its neighbours for as long as every number was short enough to fit the minimum width. Past a thousand lines it stopped agreeing: the four-digit rows widened their gutter and started their code a few pixels further right than the three-digit rows above them, so a long file developed a visible step in its left margin — and scrolling across the boundary made the whole body of the file twitch. The gutter is now sized once for the document, from the digit count of its last line, so every row starts its code at the same place. Markdown keeps room for its fold chevrons in the same measurement. Nothing about the numbers, the folds, the change marks or the wrapping changes; the column simply stops moving.
- **(feat) Closing a session can now save it on the way out.** The close prompt offered *Cancel* and *Close session*, and the warning underneath it — live terminals are memory-only and cannot be recovered — described exactly the moment at which you would most want to keep the arrangement you were about to destroy. Keeping it meant backing out of the dialog, opening **Sessions… → Save Session**, and closing the tab again. The prompt now has a third button, **Save and close**, which stores the group as a reusable preset and only then tears it down. It is the same save the menu item performs, on the same group: a tab already tied to a saved preset updates that preset in place, and one that is not gets a new one, so the button never asks you to name anything mid-close. **A save that fails cancels the close** — the group stays exactly as it was, with the reason on the session line — because a requested save that did not happen must not cost the terminals it was meant to preserve. *Cancel*, `Escape`, and clicking outside the dialog all still keep the session; *Close session* still closes without saving; and a group whose terminals are all disconnected still closes with no dialog at all.
- **(feat) Right-click a commit in the Git graph to copy its hash or its message.** The graph at the foot of the Git sidebar was read-only in the strictest sense: a commit row expanded to show its files and nothing else, so getting a hash out of GridVibe meant reading seven characters off the screen and typing them somewhere by hand, and getting a subject meant retyping the line. Right-clicking a commit row now opens the same context menu the file rows use, with **Copy commit hash** and **Copy commit message**. The hash it copies is the **full 40-character object id**, not the abbreviation the row displays — that is what a `git show`, a branch point, or an issue reference actually wants, and an abbreviation is only unambiguous until the repository grows into it. The message it copies is the subject **without the `(HEAD -> main, tag: v1.2)` decoration** the row renders ahead of it; a subject that genuinely opens with `(fix)` or `(opt)` keeps its prefix, because the decoration is now carried as its own field rather than guessed at by stripping parentheses off the rendered line. Both entries are pure reads of what the sidebar already fetched — no request, no confirmation, no refresh — so the explorer's read-only contract is untouched, and a commit row still takes no part in multi-entry selection: it names an object in the repository, not a path under the explorer root, so it can never be swept into a delete or a copy aimed at files. A row missing either value offers that entry greyed out rather than quietly dropping it, and anything that is not a hash never reaches the clipboard. The expanded file rows beneath a commit keep the menu they already had, and clicking a row still toggles it open exactly as before.
- **(feat) `Alt+W` now works in the launcher too, and takes you back where you came from.** With multiple workspaces on, `Alt+W` walks between workspace windows — but the launcher is a *window*, not a workspace, so the shortcut did nothing there. That is exactly where it was most missed: you reach the launcher with ``Alt+` `` or the button at the head of the session tab line, do one thing, and then have to go back with the mouse, through the Workspaces card and its per-row **Open** button. Pressing `Alt+W` in the launcher now returns you to **the workspace that opened it** — the window you pressed ``Alt+` `` in, or whose launcher button you clicked — and opening the launcher from a different workspace retargets the way back, so it always means "the one I just left". The workspace it came from is a hint, never an authority: it is checked against the workspaces that are actually open every time you press the key, so a workspace closed while the launcher sat in front of it hands you to whichever workspace is still open rather than conjuring a blank window, and a launcher opened at startup — which was never handed over from anywhere — goes to the one window there is. With nothing open, the banner says so. Unlike the session page, a focused text field does not swallow the key: the launcher is almost entirely form fields and `Alt+W` means nothing to any of them (the one exception is App Settings' push-to-talk keybind box, which is meant to capture whatever you press). `Alt+Shift+W` is not a separate direction here — there is no cycle to run backwards from a window that is not a workspace — and the arrival pulse, the session tab you land on, and every other workspace-switching path are unchanged.
- **(feat) A hidden top bar comes back when you reach for it.** The chevron hides the top bar to give the panes room, and it took the `Sessions…` and `Workspace…` menus with it — which are the only place **Save Session** and **Save Workspace** live. So hiding the bar to get room took away the two controls you hide it in order to keep using, and saving your layout meant restoring the bar, saving, and hiding it again. **Resting the pointer on a small handle at the top edge now brings the bar back**, as an overlay across the top of the workspace rather than a return to the layout, so nothing below it moves and not one terminal is resized by a trip to the edge. The handle sits centred and is the *only* thing that triggers the reveal — the rest of the top edge stays inert, so travelling along it, or reaching for a pane's top corner, never summons the bar at you. It also means the reveal is marked rather than hidden behind an invisible gesture. It stays for as long as you are using it — the pointer on it, focus in it, or one of its menus open, so a menu can never close out from under you a few pixels off the bar — and hides again shortly after you move away, or immediately on `Esc`. Clicking the handle reveals the bar *and* puts focus on the first control in it, which is the keyboard route in: a hidden bar has nothing to Tab into. **Fullscreen now hides the bar too**, and reveals it exactly the same way. That is for the duration of fullscreen only: it never writes the stored setting, so leaving fullscreen gives back whatever the chevron last said, and the chevron itself steps aside while fullscreen owns the bar rather than sitting there toggling a value with nothing to show for it. Nothing about a reveal is persisted — `topbar_visible` still records the chevron and only the chevron, and every workspace save, restore, and cross-window sync is unchanged.
- **(fix) The workspace top bar no longer offers a redundant “Refresh all” button.** The control only re-read session status and shape; it did not reset or reload every pane, despite sitting beside the pane-level reset controls and being labelled as though it did. GridVibe already performs that reconciliation from Socket.IO updates and retains its 15-second fallback while the socket is unavailable, so removing the button changes no automatic recovery behaviour. Per-pane **Reset view** remains available for explicitly resetting a terminal display or reloading an explorer or browser pane.
- **(fix) The close/restart dialog no longer asks the same question twice.** Under "Choose whether to save current changes before GridVibe closes." sat a second line — "Choose what GridVibe should do before continuing." — saying the same thing again in different words, and it was there every time the dialog opened. That line is the dialog's status region, which exists to report progress ("Saving current state…") and failures; it was simply being pre-filled with filler copy while there was nothing to report. It now stays empty, and collapses out of the layout entirely, until the dialog actually has something to say. The subtitle, the three choices, and every progress and error message are unchanged.
- **(feat) Select several files in an explorer pane and act on all of them at once.** The context menu only ever worked on the row you right-clicked, so deleting nine files meant nine right-clicks and nine confirmations. **`Ctrl`-click now adds or removes a row and `Shift`-click takes a range**, in the Preview listing and the Files tree alike; right-clicking inside the selection points **Copy**, **Cut**, **Delete**, **Download** and **Copy path** at the whole set, and right-clicking anywhere else collapses back to that one row, so a selection you forgot about somewhere else can never be swept into a delete you aimed at a single file. A plain click is untouched: it opens the file and clears any selection, exactly as before, and **`Escape` drops the selection** so getting out of one does not mean un-clicking every row or opening a file you did not want. It goes to the explorer pane you last interacted with — the same way `Ctrl+Shift+F` already picks its pane — so it still works after clicking blank space, the toolbar, or away and back, rather than only while a row happens to hold focus. Escape is a shared key, so it is claimed narrowly: only unmodified, only outside a text field, only when something is actually selected, and only when nothing else wants it — a context menu, the in-place editor, a find bar, either search box, any open dialog or header menu all keep it, so cancelling a delete confirmation never also throws away the selection it was about. Clearing takes the keyboard focus off the row too, since a focused row is painted with the same fill as a selected one and would otherwise be left looking half-selected. **Nothing about the backend contract moved.** There is no bulk endpoint and no archive download — a batch is N of the same bounded, root-confined, revision-checked requests a single action always made, run in order under one busy hold, with **one** confirmation naming the count and **one** refresh at the end instead of one per entry. That last part is not just speed: reloading between two requests re-reads the pane's root and would have quietly abandoned the rest of the batch. Because each entry is checked independently, a partial failure is reported as one ("Deleted 2 of 4; 2 failed…") and **Retry** replays only what failed — and only when every failure left the filesystem untouched, since a partly applied batch has to be looked at rather than repeated. Selecting a folder *and* something inside it is resolved rather than reported: the folder's own recursive delete or copy already covers the child, and sending both would fail one of them on a revision check. Selections are per pane, never cross the tree and the listing at once, are dropped when the pane's root changes, and are never persisted. **Rename stays single-entry** — it takes one exact name in the entry's own folder — and shows as disabled rather than disappearing, so the menu does not reshuffle under the pointer. Downloads past ten files ask first, since each one is its own transfer (and, in the native window, its own Save dialog).

## 1.9.0 - 2026-08-11

- **An SSH workspace now comes back from a restart logged in, instead of filling every pane with an authentication error.** Restoring a saved workspace could leave every terminal in it showing `Connection Error — No authentication methods available`, with a **Retry connection** button that could never succeed, because the relaunched panes had no credential to retry with either. Saving the workspace again, saving the session, saving both — none of it helped. `runtime_state.json` deliberately never stores a password, so a restored SSH pane takes its credential from the saved session its tab refers to; the trouble was that the most ordinary way of starting a session leaves the tab referring to nothing. Picking a host from the launcher's **saved-target menu** fills the address *and* fetches that saved session's password for you, and then deliberately drops the session identity, which is what lets you open the same machine several times over instead of one launch stealing the tab that owns it. The group is saved with no reference to follow, and restore had nowhere to look. **Restore now resolves a pane's credential from its own host, user, and port** — the same lookup that target menu already performs, over the same saved sessions, storing nothing new anywhere. A saved session the tab explicitly refers to still wins; the fallback only fills panes that would otherwise come back with nothing. Two rules keep it honest: a target that several saved sessions **disagree** about is skipped rather than guessed at, because restoring the wrong account's password could lock somebody out, and a pane naming a host you have never saved is left alone. Separately, and feeding the same failure: **Save Session** from the terminal page stored a session with *no* password at all — the browser has none to send, it never receives one — and once that credentialed-with-nothing session existed, the exit dialog's **Save open sessions + workspaces** could never repair it, since the rule that stops a re-save downgrading a working password also protected an empty one. Both of those saves now fill in the password the pane actually authenticated with, **only when the stored one is empty** and **only when the saved session still names that exact host, user, and port**, so an existing credential is never replaced and one since pointed at another machine cannot inherit a login it has no business having. It is encrypted at rest like every other saved password and is not echoed back in the save response. And because SSH authentication happens *after* a launch reports success, launching a saved session that has no stored password now says so, rather than reporting a clean launch and filling the panes with errors a moment later — a warning, never a block, since key authentication is a legitimate reason to have none. `runtime_state.json` remains password-free throughout.
- **`Alt`-click a fold arrow in the Files tree to fold a whole level.** Tidying the tree was one click per folder: browse into a few branches and putting it back took as many clicks as it took to open, in whatever order left the arrows where you could still reach them. The Markdown **Source** viewer has folded by level for a while, and the tree now does the same — holding **`Alt`** while clicking a folder's fold arrow applies the fold to **every folder sharing that folder's parent** instead of just the clicked one. The new state mirrors the folder you clicked, exactly as in the Markdown viewer: `Alt`-clicking an open folder folds that level, `Alt`-clicking a closed one opens it. Because the top-level folders are all siblings of each other, `Alt`-clicking any open top-level folder collapses the entire tree in one action — the case this started from. The tree's notion of "this level" is *siblings*, not depth: `Alt`-clicking `src/api` folds the folders inside `src/`, and leaves `docs/` and everything else alone, which is what makes the gesture usable partway down a branch. Folding a level also **forgets** the expansions beneath it, so reopening one of those folders gives you a collapsed folder rather than springing the old subtree back — "fold everything I opened" hands back a clean tree. **The tree also stays where you were looking.** Folding a level takes most of the rows out from under the scroll position, and a browser answers a shrunken scroll height by clamping the scroll to the new bottom — so the panel used to land somewhere with no relation to what you clicked. The folder whose arrow you clicked is now the anchor: the tree scrolls by the minimum needed to bring that row back into view, and leaves it alone if it never left, so nothing jumps when the fold was already on screen. Unfolding re-anchors the same way once the level has filled in, since folders listed above the clicked one push it down the panel. Unfolding a level lists each folder's contents so its children are there to see, a few at a time so a wide level over SSH does not fire one request per folder at once, and folders already listed come off the cache without a refetch. Folding is pure state and fetches nothing. A plain click is unchanged in every respect, deeper folds included, and the fold arrow still never navigates the Preview tab. The arrow's tooltip now advertises the shortcut.
- **Find a file by name from the Files tree.** The tree panel's head now carries a filter box next to the FILES label, with the same **Aa** / **ab** / **.\*** toggles as the search sidebar. Typing filters the tree to every file and folder under the explorer root whose *name* matches, nested under the folders that contain them and with the matched part of each name highlighted in place — the rows behave exactly like ordinary tree rows, so a hit opens, reveals, or copies its path the way it always did. This is a name search, not a content one: file contents are never read, and the repository search sidebar (`Ctrl+Shift+F`) remains the place to find a string *inside* files. `Enter` opens the first hit and `Esc` clears the box and puts the browsable tree back. It runs server-side and read-only on both backends — a bounded breadth-first scan locally, one bounded `find` over SSH — walking directory metadata only, skipping *into* the usual heavy directories (`.git`, `node_modules`, `.venv`, `__pycache__`, which are still listed by name), and stopping at a depth, entry, result, and time limit rather than running long; whatever it stopped at is reported under the results. The query is never persisted: it lives with the pane, like the search sidebar's.
- **A long download or search in a remote explorer pane no longer breaks if you keep using that pane.** Explorer panes over SSH share one connection per session instead of dialling a new one for every click, and a connection nobody has used for a minute gets hung up. "Used" was recorded when a request picked the connection up and when it put it back down — never in between — so an operation that ran longer than a minute, a large file download or a repository-wide search on a slow link, looked untouched for its whole duration. It was safe while it was the only thing happening. But the hang-up check runs whenever a request in the same pane starts, so browsing a folder, opening a file, or the pane's own background refresh landing during that minute would close the connection out from under the transfer, and it failed partway through with a connection error. The pane now counts how many requests are actually holding a connection and never hangs up one that is in use; once the last one finishes, the idle minute starts as before. Nothing about the timeout, the pooling, or what happens to genuinely idle connections has changed.
- **A pane echoing single keystrokes no longer slows down every other pane on the page.** Each session keeps a short rolling buffer of its recent output so a window joining late can replay the last screenful. That buffer is bounded by *characters* rather than by pieces, so how many pieces it holds is decided entirely by how big they arrive: bulk output comes in 4 KB reads and fills it with thirteen, while single-character echo — the fallback a local shell takes when it cannot read more than one byte at a time — fills it with fifty thousand. Every new piece then re-added the length of every piece already in there, and it did so while holding the one lock that every terminal's output pump shares, so the cost was never paid by the busy pane alone: **2.4 ms per character**, with every other pane in every other window waiting behind it. An ordinary interactive line, at 64 characters a chunk, cost 40 µs of the same shared lock. Nothing was ever lost or corrupted by this — it was pure latency, and it arrived exactly when it was least welcome, since the worst case only begins once the buffer is full. The buffer now carries its own running length and adjusts it as pieces go in and fall off the end, which is what the trimming step was already computing anyway. The same three measurements are now **0.6 µs, 0.8 µs and 0.9 µs** — the same cost whatever the buffer holds, which is the property that was actually missing. Replay contents, buffer size, and everything downstream are unchanged.
- **Setting `cors_origins` to `"*"` now says, once at startup, what it switches off.** It is one value in `config.json`, it is easy to reach for while getting a reverse proxy or a custom port working, and it disables **both** of GridVibe's origin defences rather than the one it appears to name. Socket.IO stops checking origins, so any page open in your browser can connect to `localhost` and write to your live shells; and the cross-origin write guard reads the same `*` as *allow everything*, so state-changing HTTP requests stop being checked too. GridVibe binds to loopback and has no authentication by design — the same-origin default **is** the boundary, and `*` removes it. Wanting that in front of a proxy is legitimate, so it is still honoured exactly as written: nothing is refused and no behaviour changed. It is simply no longer silent. One warning line at startup names both defences and points at the alternative — name the proxy's origin rather than using `*` — printed directly under the line that already reports the effective allowlist, so the first lines of a run describe the whole origin posture instead of half of it.
- **Internal — audit follow-ups.** A browser pane is now recognised as one by the connection dispatcher itself rather than only by its callers. Browser panes run on the local-shell connection mode, so a caller that dispatched one without checking first would not have hit an error — it would have got a perfectly working shell with the pane's tab URL typed at the prompt. Every current caller does check, and the one that does not is unreachable today; the branch now sits at the single place that resolves what kind of pane something is, which is where the same class of bug was closed for explorer panes. Separately, two voice-status tests patched the availability checks they were exercising but not the optional `websocket-client` import that both Vosk paths short-circuit on before ever reaching them — so on a machine without that package they failed on an assertion about something else entirely. They now patch it, as their faster-whisper sibling already did.
- **A recording that ends by accident is now cleaned up, and dictation has a five-minute ceiling.** Voice state was only ever released by stopping the recording yourself: close the tab mid-sentence, suspend the laptop, lose the network, or let the browser crash, and that recording's buffered audio stayed in memory for the life of the process — along with, on Vosk, a WebSocket to the recognizer that was never closed. Nothing surfaced it and nothing recovered it; the memory simply never came back until GridVibe restarted. Each recording now remembers the window that started it, and a window that disappears releases exactly its own: buffered audio dropped, recognizer connection closed, nothing transcribed and nothing sent, since the window that would have received the words is gone. Two windows recording the same pane behave the way you would expect — the second takes over, and the first one's disappearance does not stop the recording that is still running. Separately, faster-whisper holds everything you say in memory until you stop, at roughly 1.9 MB per minute, and had no ceiling at all: a push-to-talk key held down — or wedged by a window that never saw it come back up — grew that buffer for as long as it lasted, then handed the whole thing to one transcription pass. **Recording now stops on its own at five minutes.** It is not a discard: everything said up to that point is transcribed and delivered exactly as if you had stopped it yourself, and the pane says why it stopped so you can carry on with a fresh recording.
- **`--port` and `--host` no longer leave you with terminals that accept no input.** Both flags are documented, both bound the server where you asked, and both then broke every terminal on the page. The allowed Socket.IO origins were computed once at import from `config.json`, while the address the server actually binds was resolved separately by the entry point, where the flag correctly wins — so `python main.py --port 8080` served the page on 8080 and authorised 5050. The failure was worse than a refusal: the first handshake **succeeded**, because browsers send no `Origin` on a same-origin GET, so panes appeared to connect. The WebSocket upgrade was then rejected (a WebSocket handshake always carries `Origin`), leaving the transport stuck on long-polling, and the polling data POSTs that carry terminal input were rejected too in Chromium and Safari. What you saw was a workspace that loaded, connected, and then sat there — no input, no output — with nothing but `… is not an accepted origin` in the log. HTTP writes kept working throughout, which is exactly why nothing looked broken until you typed. The origins are now derived from the settings the server actually resolved, applied at startup, and logged once so the effective allowlist is visible on the first line rather than inferred from a failure. `--host 0.0.0.0` browsed by LAN IP is covered too: a wildcard bind names no origin anyone can enumerate, so with no explicit configuration GridVibe now also trusts the host a request was genuinely addressed to — the same rule the cross-origin write guard has always applied, which is why the two defences disagreed in the first place. Nothing was loosened: a hostile origin is rejected as before, and an explicit `security.cors_origins` list is still honoured exactly as written, request host included only if you list it. **The `security.cors_origins` workaround people used to make a custom port work is no longer needed** — if you added one for that reason, you can drop it and get the same-origin default back.
- **You can now dictate into a file, and leaving a session group finally leaves the editor.** Voice input only ever reached a terminal. The explorer's in-place editor — the one surface in GridVibe where you write prose and code rather than commands — had no way to use it: the pane-header mic is hidden on explorer panes, and push-to-talk targets the focused *terminal*, so there was nothing to click and no key to hold. Open a file for editing with voice input enabled and the editor now has its own 🎙️ beside **Save** and **Cancel**. It exists only while you are editing, so there is no dead button to explain. Dictated words land at the caret — replacing a selection if you had one, gaining a single leading space only where one belongs, never a line break — and from that moment they are ordinary buffer text: same dirty marker, same unsaved-changes prompts, same revision-checked save. `Ctrl+Z` puts the buffer back the way it was in **one** step rather than skipping past the dictated block, which is why insertion goes through the browser's own text-insertion path instead of the shortcut the Tab key uses. **Save and dictation cannot overwrite each other.** Save is held for as long as a capture belongs to that buffer — and, importantly, for a bounded moment *after* you stop, because the shipped faster-whisper engine only produces the transcript once recording ends; a `Ctrl+S` in that gap used to be exactly where the words would have gone missing. If the transcript never arrives the editor frees itself after five seconds and says so, and a transcript that outlives its editor is dropped with a reason rather than silently applied somewhere else. Still one recorder at a time across the whole page — an editor and a terminal stop each other exactly as two terminals do — and the recording ring and live partial preview now follow whichever mic you can actually see. Push-to-talk reaches the editor only when your keybind carries `Ctrl`, `Alt`, or `Cmd`: a bare-letter keybind would start recording *and* eat that letter out of the file every time you typed it, which a terminal can shrug off and a text buffer cannot. Nothing is saved to disk by any of this, and no pane without a terminal or an open editor can be sent transcript text at all. **Separately, and not a voice problem:** switching session groups with a file open for editing left the pane wedged. The switch asks to discard unsaved changes and then dropped the edit *state* without rebuilding the *view* — and since a group switch caches its panes exactly as they stand rather than rebuilding them, you came back to a read-only file still wearing **Save**, **Cancel** and a greyed-out Source/Preview switcher, with **Cancel** the only way out. A clean editor was not even asked about and simply sailed through. Switching groups now genuinely does what the prompt promises: every open editor closes properly first, dirty ones after you confirm and clean ones silently, so the pane you return to is the ordinary file view you would have got by pressing Cancel yourself.
- **The launch button now names what it launches, and notice banners are centred.** The split CTA read **Launch Workspace** / *into <workspace>* — two lines that between them only ever said "workspace", and never said which setup was about to run. Importing a saved session announced itself in the green banner and then, six seconds later, left no trace: the form held the imported preset but the button still offered the same anonymous sentence, so the one thing you needed to confirm before clicking — *am I launching the preset I just imported, or the scratch setup that was here before?* — was the one thing nothing on screen answered. The primary line now names the session (**Launch my-preset**, or **Launch new session** when the form is a scratch setup or the default preset) in a larger weight, with *into <workspace>* under it as before, and it updates the moment a preset is imported, saved, or dropped. A long preset name ellipsizes and the full sentence, destination included, is on the button's tooltip. Nothing about what the button does changed, and with multiple workspaces off it still degrades to the single line. Separately, the notification banner's text is now centred rather than left-aligned behind its icon, so a short confirmation reads as the page's one announcement instead of a fragment stranded in the corner.
- **Launcher messages now appear in one place, and a failed update is reported once instead of twice.** The launcher had two unrelated message lines and no rule about which one a message belonged to. Most outcomes — *Launch failed*, *Could not save the workspace*, *Settings save failed* — were written into the helper line inside step **01 Terminal Layout**, in the opposite column from whatever had actually failed and nowhere near anything that says "errors appear here". Update and restart outcomes were written to *both* lines at once: the same failure in two corners, with two different prefixes, one of which quietly vanished after six seconds while the other stayed forever. App Settings managed a third variant, reporting its success to one line and its failure to the other. There is now a single **notification banner** directly under the title bar, in its own row alongside the restore banner, and every launcher message goes there. One message is on screen at a time — a new one of any severity replaces the last, so nothing stacks up or scrolls away. **Failures and warnings stay until you dismiss them or something replaces them; confirmations clear themselves after six seconds.** Dismissing is purely cosmetic: it cancels nothing and changes no behaviour. Severity now reads without relying on colour — each state has its own icon, border, and tint, and the banner is announced to screen readers. Long errors wrap and scroll inside the banner instead of pushing the page around, and a git error full of unbroken paths cannot stretch the layout. Errors are also echoed to the browser console. The banner is launcher content, so a dialog opened on top of it covers it — a failure raised while App Settings or the restore chooser is open waits and is still there when the dialog closes. Alongside this, the message copy itself got a pass: one prefix per kind of failure rather than a prefix from the caller *and* one from the server, no more dangling "Launch failed: ." when a request fails without a message, and the "— try again" tacked onto the end of failures is gone (the retry was always the button that stayed put, not the words). A launch refused for a missing SSH host or local repository folder now outlines and focuses the field it means.
- **Two windows on one workspace no longer block saving on exit, and voluntary close/restart is a third writer of workspace shape.** A workspace open in two browser tabs reports its window chrome twice — the front session tab is per window, and a top-bar toggle in one window is not pushed to the other — and the save-on-exit coordinator treated that ordinary disagreement as a corrupt payload: **Save open workspaces**, **Save open sessions + workspaces**, and the launcher's per-row **Save** all failed with a retryable error for as long as both tabs were open, naming an opaque workspace id and no action you could take. *Continue without saving* still worked, which meant the only way out of the failure cost exactly the changes the save existed to keep. A disagreement is now resolved rather than refused: **a workspace's chrome is whichever window most recently joined**, applied per field, so a window that reports nothing about the top bar does not erase its sibling's opinion, and the newest window wins even when an older one answers first. A window still pointing at a session tab that was closed from another window a moment earlier drops that one hint rather than the whole save — the capture falls back to the server's own active tab, which the snapshot writer re-validates against the captured groups anyway. Malformed *types* still fail, unchanged: a non-boolean top-bar value or an out-of-range native zoom is a broken client, not two honest windows disagreeing. Alongside that, a window that drops while a save is in flight now resolves that save immediately with the accurate *stale window* reason instead of stalling for the full five-second flush wait and then blaming a timeout, and a window that deliberately leaves mid-save is forgotten instead of being counted as a failed one. And for the record, correcting a promise made in 1.8.0: workspace shape now has **three** writers, not two — the autosave timer, **Save Workspace** (in-window, or the launcher's per-row **Save**), and a successful save on voluntary close/restart.
- **Explorer theme overrides can no longer pile up dead session IDs, and forgetting a workspace drops its cached top-bar state.** The explorer light/dark override cache in `localStorage` was keyed by an ephemeral session ID that changes on every restart, and no path ever removed an entry — long-running use grew the object one dead key per pane per run, forever. The manager has owned the authoritative theme since the presentation transactions landed, so the cache is now re-bounded to the panes that actually exist on every theme write and on every grid build, and it empties itself completely when no explorer pane remains. Likewise, **Forget** and **Close and forget** now remove the workspace's cached top-bar visibility key together with its snapshot, and a failed forget keeps both so a retry sees the same state. Lifecycle saves (close/restart and the launcher's per-workspace **Save**) also log shape-only diagnostics — workspace IDs, revisions, preset/workspace counts, and failure categories — never paths, commands, file contents, or payloads.
- **A damaged saved workspace now fails visibly instead of coming back a pane short, and a capacity refusal tells you what to change.** A stored pane was only ever checked for the *names* of its fields, never the types of their values, so what a corrupt snapshot did to your restore came down to a coincidence: `explorer_tab_views: "x"` and `browser_active_tab: "abc"` happened to make an internal conversion raise, so that pane was quietly skipped and the tab reopened one pane smaller — reported as a complete restore — while `explorer_open_tabs: "abc"` happened *not* to raise, so the string was converted into the three tabs `a`, `b` and `c`, installed as live state, and written back to disk by the next autosave. Neither outcome was announced, and the restore chooser's "2 groups, 5 panes" could describe something a restore would never actually start. Every nested explorer and browser field now goes through the one canonical normalizer, which checks types and rejects rather than converting; a stored pane it rejects costs its whole group, so the chooser's counts and the shape a restore replays are once again the same thing, and the damaged slot is left untouched on disk for diagnosis and for a later fix rather than being rewritten or hidden. The same rule now applies to a launch request, so a malformed pane can no longer open a smaller group and call it exact. The boundary is deliberately narrow: **launchable shape fails, window chrome degrades** — an invalid stored top-bar visibility or Markdown appearance value still falls back to its default rather than costing you the workspace. Values of the right type are still bounded, not rejected, and a snapshot written by an older GridVibe that simply lacks the newer fields restores exactly as before. Separately, refusing a group that no longer fits `max_sessions` now says which number to raise the setting to — "This group needs 6 panes, but the current max_sessions limit is 4. Raise max_sessions to 6 in App Settings, then retry." — in place of the old "Maximum 4 sessions allowed", on the launch, split, and per-tab restore paths alike. The stored preset and the stored snapshot are still left byte-for-byte untouched by the refusal.
- **Saved explorers now return exactly as arranged without restoring stale content coordinates.** Explorer presentation records are versioned and now preserve per-panel horizontal/vertical scroll, directory scroll, Files/Git sidebar scroll and width, expanded Files-tree paths, expanded Git commits, view mode and Diff target, zoom, wrapping, folds, theme, and ordered tabs across reusable session presets, manual workspace saves, autosave, and restart restore. Preview/Diff intent survives an external edit, while scroll and folds are applied only to the matching file/directory/rendered-Diff revision; staged Diff identity follows the actual patch/index result instead of only the working file. Fetched tree/Git/search data and Search queries/results remain ephemeral. A captured explorer root is no longer narrowed to its current child directory during local or SSH restore. Markdown preset/font/source-font are now one workspace-scoped value carried by the existing ordered workspace-presentation transaction and runtime snapshot; old per-pane values migrate once, and `localStorage` is only a startup cache. Existing flat explorer records remain readable.
- **A lost workspace window can no longer block saving on exit, workspace names are unique, and the launcher can save one workspace.** Workspace windows now keep a stable per-window id in `sessionStorage`, so a reload replaces its own lifecycle registration even when the page never fired `pagehide` (a crash, a kill, a network drop, a suspended laptop); a disconnected window still blocks the save-or-exit flush while the loss is fresh, but once it has been gone past a two-minute grace period it is treated as departed instead of permanently failing every later save, and window registrations are bounded per workspace. Workspace labels now have one owner across both live workspaces and saved snapshots: creating, renaming, or launching into a workspace with a name that is already taken (case- and whitespace-insensitively) is refused with a `409` that names the conflicting kind and offers the matching action inline — open the live namesake, forget the saved snapshot, or pick another name — while unlabelled workspaces stay unconstrained and nothing is auto-renamed or auto-forgotten. **Launch into a new workspace** now always opens with a blank name and checks that name inside the popup before it can become the Launch button's destination; a saved or live collision leaves the popup open with the exact server error, and even a collision that races the final launch returns to the same fresh popup instead of retaining the rejected draft. The launcher's Workspaces card gains a per-row **Save** button that runs the same flush handshake as in-window **Save Workspace** scoped to that one workspace — it flushes the owning window before capturing or refuses, captures only that workspace's slot, never touches saved sessions, and reports a retryable error when no window is reachable instead of silently capturing stale server state.
- **Close and restart now use one process-wide save-or-exit transaction.** The manual restart button, update restart, explicit browser close, and native launcher X now open the same in-page choices: continue without saving current changes, save every open workspace, or save/update every open reusable session and then save every workspace. A server-owned coordinator asks every connected workspace window to flush the ordered presentation queue first, waits for a bounded acknowledgement, carries that window's active group, native zoom, and top-bar value into one all-live workspace commit, and reports a disconnected/stale window instead of guessing. Reusable presets commit before workspace snapshots so restored SSH groups can recover an encrypted password from the matching preset while `runtime_state.json` remains password-free. A timeout, preset failure, or workspace-write failure keeps GridVibe and all live shells open with the same three choices still available; selecting the same save choice tries it again, while the first choice continues without saving. Partial preset success is reported and is never silently rolled back. Browser and native teardown now require a one-use successful lifecycle decision, so no voluntary exit surface can bypass the choice. Native X defers its synchronous JavaScript request until after pywebview's locked closing callback returns, preventing the WebView2 deadlock caused by evaluating JavaScript inside that callback. The old launcher-side loop over `/api/runtime-state/save` and its cross-window top-bar `localStorage` read are gone.
- **Lowering `max_sessions` no longer mutates stored session shape.** Saved-session normalization and custom split geometry now use an immutable 64-pane schema ceiling rather than the current launch preference. A wider preset stays intact when it is read or when an unrelated preset is changed, and runtime-state reads preserve valid high `originSlot` values instead of clamping several slots onto a different pane. Unrepresentable geometry is rejected as geometry rather than rewritten into a valid-looking layout. The current preference is still enforced at launch.
- **Saved sessions are now written as durably as workspace snapshots, and a first start can no longer lose its encryption key.** `saved_sessions.json` is the one GridVibe file holding an encrypted SSH password, and it was the least protected: saving, deleting, and picking the last-used preset were each a separate *load, change in memory, save the whole file* pair with no lock, so two of them running at once — two launcher windows, a save while a delete was in flight, a second GridVibe process — each read the same list and each wrote its own version back, and whichever finished last silently discarded the other's preset. The write itself truncated the live file and refilled it, so an interruption left invalid JSON; an unreadable file was then reported as *no saved sessions*, and the next successful save made that emptiness permanent. Deleting the last preset even answered "updated successfully" when the removal had failed and the presets were still on disk. Every change now runs as **one transaction**: the read and the write happen together under an in-process lock plus an OS-level `saved_sessions.json.lock`, so a concurrent unrelated change survives instead of being overwritten. The commit goes to a uniquely named scratch file and is moved into place atomically after the previous version is kept as `saved_sessions.json.bak`, so an interrupted save leaves the old presets intact rather than a half-written file. A file that cannot be read, or that is not a preset store at all, is moved aside as `saved_sessions.json.corrupt-<timestamp>` and the last-good backup is loaded in its place — the evidence survives, and no later save overwrites it. And a write or delete that does not reach the disk now raises rather than being logged and swallowed: the save, delete, and last-used-preset routes answer with the same retryable failure the workspace-save route already used, instead of echoing the preset back as saved. Separately, the Fernet key: `_get_encryption_key()` checked whether `.encryption_key` existed and then created it, in two steps, with a write that created the file empty and filled it afterwards. Two processes starting together could therefore generate two different keys — the loser keeping a cipher for a key no longer on disk — and, worse, a process importing the module during that empty window read zero bytes and **failed to start at all**. The key is now written complete to a sibling temp file and claimed under its real name with a single syscall that fails rather than clobbers, so both processes converge on one key and no reader can ever observe a partial one. The stored JSON shape and the encryption format are unchanged; nothing you have saved needs migrating.
- **The Files tree now scrolls the highlighted file into view.** Opening a file already marked its row in the Files sidebar and expanded the folders above it, but the panel kept whatever scroll position it had — in a long tree the highlight was frequently off screen, so the one cue that says *this is the file you are looking at* could not be seen without hunting for it. Every reveal (opening a file, browsing to a directory, opening the sidebar with a file already open) now scrolls the tree panel by the minimum needed to show that row, with one row of margin so it never lands flush against an edge. A row already in view is left alone, so clicking around inside the tree does not jump, and only the tree panel scrolls — the pane around it stays put.

## 1.8.0 - 2026-08-07

- **The back-to-launcher button moved to the head of the session tab line, and `` Alt+` `` now opens the launcher.** It used to sit last in the top bar, which meant it disappeared along with everything else whenever the bar was collapsed — the one control whose whole job is *leave this window* was hidden behind first restoring the bar. It now sits at the start of the session tab line, ahead of the first tab, next to the tabs it creates and visible whether the top bar is shown or not. The keybind is the key immediately left of `1`, matched by physical key position rather than by the character it types, so a layout where that key is a dead accent reaches the launcher just the same; a focused terminal hands the combination up to the window instead of sending `` ESC ` `` to the shell, exactly as `Alt+W` already does. Nothing about what the button does changed — same handler, same native-window-then-browser-tab fallback.
- **A workspace you have open is never dropped from restore state, and a slot is only offered if it can actually be relaunched.** Two ways the restore chooser could lie to you. **(1)** Automatic snapshots are capped at twelve so `runtime_state.json` does not grow one slot per workspace ever autosaved — but the cap was applied to *every* unpinned slot, live or closed. One autosave tick stamps every workspace it captured with the same `saved_at`, so with a thirteenth workspace open the timestamps tied and the retention tie-breaker fell through to the opaque workspace id: whichever workspaces happened to sort low silently lost their snapshot, while you were looking at them. The cap now only ever collects **closed** slots, oldest first. A workspace that is live right now keeps its snapshot however many you have open — exceeding the cap for the duration is the lesser evil against losing the shape of a workspace on screen, and the excess clears itself as those workspaces close. A slot you saved by hand is exempt as before. **(2)** A slot was offered on two checks — it has a list of groups, and its origin is recognised — and nothing looked inside. A group left with no panes by a truncated write was therefore counted in the chooser as "1 group, 0 panes" and then relaunched nothing; the summary you chose from and the shape a restore replayed were computed by two different pieces of code that could disagree. Both now read through one validation gate: a group with no usable pane, or an absurd pane count, is dropped from the offer rather than advertised, a slot left with no valid group is not offered at all, and the group and pane counts on the row are exactly what a restore of it would start. Field-level shape is normalised on the way out too — a pane keeps only the launch fields capture actually writes, so a `password` hand-added to the state file cannot re-enter a launch body, and a stored layout that no longer matches its pane count is dropped instead of replayed. Nothing is rewritten on disk by a read: the stored bytes and the last-good backup are left exactly as they were, for diagnosis. Lowering `max_sessions` is deliberately *not* treated as corruption — that slot stays on offer and the launch answers per tab with "Maximum N sessions allowed" and its usual **Retry**, which is something you can act on, rather than the workspace vanishing from the chooser with no explanation.
- **Explorer Preview now restores correctly when it was browsing the repository root.** The root is represented by an empty relative path, but Preview-tab persistence treated that value as if no directory had ever been loaded. Restoring such a workspace therefore showed an empty Preview and left the path bar as inert text until the Files tree was clicked; subdirectories did not fail because their relative paths were non-empty. Preview state now distinguishes an absent directory from the intentionally empty root path, preserves that distinction through workspace saves and close-driven pane rebuilds, and immediately reloads the root listing and its live breadcrumb after restore. Invalid or escaping persisted paths are still discarded.
- **The workspace window you land in pulses, so a swap is visible.** Two GridVibe windows look alike — same chrome, same grid, only the content differs — so `Alt+W`, **Workspace ▸ Open Workspace** and **Open** in the launcher's Workspaces card all handed focus to another window with nothing announcing it; on a second screen, or with both windows visible at once, the only way to tell the switch had happened was to read the tab names. The window receiving focus now flashes a ring around its viewport once. It is armed at the departing end in the two dispatchers every swap already goes through (`focusWorkspaceWindow` / `openWorkspaceWindow` in `workspaces.js`), so a surface added later cannot forget it, and claimed at the arriving end by the window that matches the request — once, and only within a short window, so a request nobody arrives on expires instead of pulsing at some unrelated moment. The request is stored rather than broadcast, which is what lets a workspace that had no window yet pulse when its fresh page boots. The ring never takes a click, and `prefers-reduced-motion` gets a single quiet fade instead of the two beats.
- **Restoring a workspace gives you back the workspace you saved, not the presets you edited since.** A restored tab that had come from a saved session was rebuilt from that session's *current* configuration — "latest preset wins" — so editing a preset silently rewrote every saved workspace that referenced it. A three-pane workspace you saved last week came back as whatever the preset had since been edited down to, with the preset's name instead of the tab's, and its stored split geometry thrown away because the pane count no longer matched. No workspace save was involved: the shape simply changed underneath you. The captured snapshot is now the only source of a restored tab's shape — names, pane count, modes, directories, commands, and both layouts are replayed exactly as captured. A preset still contributes the one thing a snapshot deliberately never holds, its SSH password, and only onto a pane that still names that preset's host, user, and port; a preset that has since been pointed at another machine keeps its password to itself, and the pane comes back with its own shape and its usual **Retry** rather than being reshaped to fit a credential. Editing a saved session now changes the next launch and nothing else.
- **Asking to restore twice reopens a workspace once, and both modes ask the same way.** Restore checked whether a workspace had tabs yet and then, in separate steps, created it and launched its groups — so two requests arriving together (a double click, two launcher windows, a window and a browser tab) both passed the check: the main workspace came back with every tab duplicated, and a named workspace failed outright with an internal "Workspace already exists". A restore now claims its workspace for the duration and the second request is told, plainly, that one is already running. With multiple workspaces off, the launcher's restore banner also stopped rebuilding the workspace itself: it used to loop over the individual launch calls in the browser, re-resolving presets on the way, which meant it could stop half way through a network failure, could restore on top of a workspace that already had tabs, and did not apply the saved workspace name. Both modes now go through the one server-side restore, which reports what actually started, tab by tab.
- **Two saved workspaces that use the same saved session are no longer restored half-way.** A saved session can be open in only one workspace at a time, but nothing stopped two saved *workspaces* from both remembering one — closing workspaces deliberately keeps their snapshots, so this accumulates on its own. Selecting both in the restore chooser used to reopen whichever the request happened to list first and quietly hand the other one back a tab short. The selection is now checked before anything is launched: the whole request is refused, the clash is named, and nothing changes until you deselect one side and restore them one at a time. A saved session already open in a workspace you did *not* select is unchanged — that tab is still reported as skipped while the rest of its workspace comes back.
- **A session tab now appears complete or not at all, and two saved sessions can no longer overwrite each other.** Launching a group used to happen in steps — create the tab, then add its panes one at a time — with the workspace unlocked between each one. An autosave tick that landed in the middle stored what it happened to see: an empty tab, one pane of three, or, when you relaunched a saved session, a tab whose old panes had already been torn down and whose new ones did not exist yet. Restoring that snapshot gave you back the half-built version. A launch is now a single transaction: the tab and every pane it contains are published together, so a save can only ever capture the shape you had before or the shape you have now. Relaunching a saved session is the same swap — its old panes are only replaced once the new ones are ready, so a relaunch that turns out to be unusable leaves the running one alone instead of emptying it. Separately, a saved session's id was flattened into its tab's id by replacing punctuation with `-`, so two presets whose ids differed only in punctuation (`a/b` and `a-b`) claimed the *same* tab: the second launch replaced the first in place, and across workspaces it closed the other workspace's live sessions before noticing the tab was not its own. Ids are now encoded reversibly, so distinct saved sessions always get distinct tabs — ordinary ids are unchanged, so nothing you already have moves. And the five-second window that protected a tab still being assembled is gone with the reason for it: an emptied tab is swept immediately, and a workspace you are launching into is held by the launch itself.

- **A workspace you closed is closed everywhere, and every "close" now tells you what it keeps.** The permanent internal `default` record used to be rendered as a workspace: after the last tab in the main workspace closed, the Workspaces card showed nothing while the launch menu still offered an empty *Main workspace — 0 sessions*, and the two lists disagreed about the same state. One predicate now decides what a user-visible workspace is — it holds a tab, or you created it deliberately empty — and the API, the Workspaces card, the launch destination menu, the Open/Move menus and the `Alt+W` cycle all read it, so a container or a launch still in flight can no longer masquerade as a workspace. Closing a pane became as explicit as closing a tab: closing the last pane within five seconds of launching used to remove the session but leave the empty group behind **forever** — nothing swept it afterwards — which kept the workspace looking occupied and its snapshot unforgettable. And the close verbs are now four separate things with four documented outcomes: closing a *window* keeps everything running, closing the last tab removes the workspace **and** its snapshot, the new **Workspace ▸ Close Workspace** (also **Close** in the launcher's Workspaces card) ends the sessions but leaves the workspace restorable, and **Close and forget** removes both — which is what the restore chooser now offers on an already-open workspace instead of a disabled button and a "close it yourself first" dead end. A deliberately empty **New Workspace** finally has an ending too: deleting it, or closing the window of one that never held a tab, releases it instead of leaving a zero-session destination behind until the next restart.

- **"Workspace saved" now means it reached the disk — and only two actions ever capture your workspace.** `runtime_state.json` was written by a function that caught every error, logged a warning, and returned as though nothing had happened: a full disk, a permission error, an antivirus lock or a failed replace produced a green *Workspace saved* confirmation for a snapshot that was never stored, and **Forget** reported success for a slot still on disk. Both now report a real failure with the existing retry wording instead of a false success, and the background autosave logs one structured error per failure streak (not one per tick) while leaving the last good file exactly where it was. Renaming a workspace also stopped being a third snapshot writer — it used to re-capture the whole workspace shape, so a cosmetic label change could freeze a half-launched or about-to-be-closed layout into the restore offer. A rename now changes the live label only, and the next autosave tick or **Save Workspace** persists it; the promise on the tin is finally literal: **the autosave timer and Save Workspace are the only two writers of workspace shape.** Alongside that, *saved manually* became durable metadata of its own rather than a side effect of who wrote the snapshot last, so a workspace you saved by hand keeps its permanent-offer pin however many times autosave refreshes it.
- **A corrupt or unrecognised `runtime_state.json` is quarantined instead of silently emptied.** An unreadable state file used to be swallowed into an empty state that the next capture overwrote for good — the evidence and every saved workspace in it were gone. The file now carries a schema version the app checks (v3; v1 and v2 files still migrate on read), every commit keeps the previous file as `runtime_state.json.bak`, and a file that cannot be parsed, or that was written by a newer GridVibe, is moved aside as `runtime_state.json.corrupt-<timestamp>` with the last-good backup loaded in its place. All of it now runs through one runtime-state store that owns the file path, the process lock, and — new — an **OS-level lock** across the whole read-modify-replace, plus a durable per-workspace revision. Two GridVibe processes sharing one state file can no longer interleave and discard each other's updates, and a close performed by one process still rejects a snapshot the other took before it, even across a restart.
- **The Source view marks what changed against `HEAD`, and clicking a mark shows the change right where it hangs.** Three pieces, one model. In a Git worktree, every line added or modified against `HEAD` carries a coloured gutter bar (green / blue), and a deletion leaves a wedge on the boundary where its lines used to be; a slim **overview column** docked beside the source paints the same marks over the whole file and doubles as the panel's scrollbar — click, drag and wheel all drive it, and clicking one of its markers jumps to that change. New with this round: the gutter marks are **buttons**. Clicking one opens a **change peek** — a compact diff of that block alone, inserted inline directly under the change with the `HEAD` lines it replaced stacked above the worktree lines that replaced them, numbered and highlighted exactly like the Diff panel. Click again, its close button, or `Escape` while focus is inside it and it collapses; a block over 200 lines renders its first 200 plus an **Open in Diff** handoff. The peek is pane state re-applied after every Source rebuild, so it survives `Ctrl+F` keystrokes, wrap toggles and Markdown folds, and it closes honestly when its block is folded away, edited over, reverted or committed out from under it — never a stale diff. Everything renders from the `git/diff?mode=head` model the pane already holds: no new endpoint, no fetch of its own, nothing mutated. The Diff panel's red/green cell tints moved into shared `--gv-diff-add-bg` / `--gv-diff-delete-bg` tokens so the peek and the panel share one palette by construction.
- **A closed workspace stays closed.** Workspace autosave read the live workspace shape and only then queued up to write `runtime_state.json`, so a tick that started moments before you closed a workspace could land *after* the close had already removed that workspace's saved slot — putting the workspace you just closed back on the restore-after-restart offer, sometimes for a shape that no longer existed. Captures are now ordered per workspace: every capture and every Forget takes a monotonic ticket before it reads anything, and a capture is dropped at commit time if a close/forget landed after its snapshot was taken. The same ordering stops an older autosave tick from overwriting a shape a later capture already stored, while an explicit **Save Workspace** still wins over an autosave that happens to finish alongside it — only closing or forgetting the workspace overrides your own save. A save that races a close of the same workspace now reports failure instead of silently re-saving it. Nothing changes for the ordinary path: autosave and Save Workspace persist exactly what they did before.
- **The test suite can no longer overwrite your saved workspaces.** `config.json` and `saved_sessions.json` were redirected to temporary files while tests ran, but `runtime_state.json` was not, so a test that exercised the real Save Workspace route wrote its fixture into the restore slot of whoever ran the suite — which then reappeared after the next restart as a workspace nobody had opened. The state file location is now overridable through `GRIDVIBE_RUNTIME_STATE_PATH`, the suite points it at a temporary directory before the app is imported, and `GRIDVIBE_TEST_MODE` makes any attempt to read or write the canonical `runtime_state.json` from a test process fail outright rather than quietly succeed.
- **A scratch session is one click away on the launcher.** **Session Source** gained a **New Session** button at the head of its toolbar, left of **Save Session**. It does exactly what **Import Session → Default session** did, minus the picker: the built-in empty preset is loaded into the form, so a throwaway setup no longer costs a dialog and a scroll past every preset you have saved. The default entry is virtual — nothing is written to `saved_sessions.json` and no saved preset is touched or overwritten. With four actions the toolbar no longer shared a row with the step title comfortably, so the **Session Source** heading now stacks its buttons underneath rather than wrapping one of them off on its own.
- **The Git sidebar's change rows now lead with the file name.** Every row in **Staged Changes** and **Changes** rendered the repository-relative path verbatim — so in the panel's narrow column the visible text was `maria/db/d…`, `models/mo…`, `yaml_db/co…`: all directory, no file (`docs/images/curent_git_unclear.png`). The one piece of information the row exists to carry was the first thing truncated away. Rows are now `name — muted directory`, the ordering an editor uses, and the directory carries an outsized flex shrink factor so it is what gets cut off first; the file name only starts to ellipsis once the directory has collapsed entirely. The full path is still on the row's `title`, and **Copy path** / **Copy relative path** / **Download file** in the right-click menu are unchanged — they read `data-explorer-copy-path`, which still holds the whole path. Two smaller changes came with it: the `M`/`A`/`?`/`D` status badge moved from the row's left edge to the right of the name, just ahead of the inline actions, so nothing sits between the pane edge and the name; and the two change lists dropped the 28px indent they inherited from the commit-history rows, where it exists to align files under their commit's graph column. History rows keep both the indent and the new name-first labelling.

- **Explorer and browser panes can now split off a terminal.** The two split controls used to be terminal-only: an explorer pane showing the exact directory you wanted a shell in offered no way to get one beside it, so you either converted the pane (losing the listing) or went back to the launcher. Both pane kinds now carry the same side-by-side and stacked controls, and both produce a *plain terminal* rather than a copy of themselves — the labels say so (**Split off a terminal beside this pane** / **below this pane**). For an explorer the new terminal starts in the directory you are currently browsing, not the one the pane was launched with, and it resolves through the same root-containment rules the pane-mode switch uses, so a path outside the configured root is refused rather than quietly opening a shell somewhere else. This works in both modes: an SSH explorer splits off an SSH terminal on the same host, port, and credentials; a Local Repo explorer or browser pane splits off a local shell relabelled with the shell it actually runs (`cmd`, `PowerShell`, `WSL (…)`) instead of inheriting the pane's `File Explorer` chrome. A browser pane's URL no longer rides along as the new shell's first command.

- **Starting a throwaway session no longer means remembering an IP — or settling for one of them.** Step 02 was pure recall: to launch anything you had to type a host, a username, a port, or a full repository path from memory, and there was no way to ask GridVibe what it already knew. Each mode button now has a caret beside it that lists the connection targets your saved sessions already use — SSH addresses under **SSH Remote**, local repository folders under **Local Repo** — deduplicated by target rather than by preset, newest first, and topped by a **Blank** entry that clears the fields the way the button always did. Picking one fills in the Step 2 fields and nothing else: the terminal rows stay at their defaults, and the launch stays *unattached* to the preset the address came from. That distinction is the point — it is a shortcut for the address, not `Import Session`, so borrowing a host does not tie you to the preset that owns it. The target list is deliberately secret-free (`GET /api/session-targets` returns hosts, ports, directories, and a `has_password` flag — never a password); the saved password is fetched from `GET /api/saved-sessions/<id>` for the one target you actually pick, so listing targets never ships every stored credential at once.
- **The default session can be launched as many times as you want.** Launching the built-in **Default Session** twice on the same host quietly replaced the first workspace instead of opening a second — and with multiple workspaces on, the second attempt was refused outright with *"already open in another workspace"*. The cause was an identity mix-up: `default-session` was sent as a saved-preset id, so every scratch launch minted the same stable group id (`saved-session-default-session`), which the launch path treats as *this preset's one group* — it replaces that group's sessions in place, and guards it against being live in two workspaces. But the built-in default is a blank *form*, not a stored preset; it owns nothing. It now carries no launch identity at all, on both sides of the wire, so every launch mints its own group and the uniqueness guard is left for the presets it was written for. Repeats are numbered instead of colliding: `10.0.0.5`, `10.0.0.5 (1)`, `10.0.0.5 (2)` — the name is checked against the live session tabs *and* the saved presets, so promoting one scratch session to a saved one makes the next launch skip past its number rather than reuse it. A saved preset still launches under its own name verbatim, and a restore still replays the name it stored — neither is renumbered.
- **A workspace you closed hours ago stops reappearing on restore.** Two faults, one symptom: a workspace nobody asked for — in testing, a one-pane explorer group left over from a throwaway preset — opened alongside the ones that were actually selected, both on a plain restore and right after clicking **Forget** on some *other* row. **(1)** The main workspace's snapshot was immortal. Emptying any other workspace forgets its shape (1.7.0 made that global, snapshot included), but that cleanup rides on the *record* being pruned, and `default`'s record is permanent by design — so it never reached the cleanup and nothing else ever cleared its slot: the capture side only overwrites a slot with a non-empty snapshot, never clears one. A group run in the main workspace once stayed on offer in the chooser forever, removable only by hand. Closing its last group (or moving that group out) now forgets its snapshot too, through a deliberately narrow rule — the close must have emptied `default` *itself*, and it must own no groups afterwards, so closing one of several tabs keeps the slot and a close in a sibling workspace never touches an unrelated empty `default`. Only explicit closes and moves take this path; a process exit does not, so restore-after-restart is exactly as before, which is the whole point of the feature. **Close all sessions** is also unchanged: like its non-default siblings, it tears down live state and keeps every snapshot. **(2)** The restore chooser threw away your selection on every re-render. Rows are built with the checkbox pre-ticked, and both **Forget** and a completed restore rebuild the list from scratch — silently re-ticking rows the user had deliberately unticked. So unticking a workspace, then forgetting a different one, quietly re-selected it, and the next **Restore** opened it. Selection now carries across renders per workspace id; only rows the render has not seen before default to ticked, and an already-live row stays unticked regardless, since it cannot be restored anyway.
- **`Alt+W` no longer opens a blank window when there is only one workspace to be in.** With a single window open the shortcut answered by opening a *second*, empty one — the opposite of a switch. The walk read `GET /api/workspaces` and treated every row as somewhere to go, but a live workspace *record* is not an open window. Two records routinely have no window: `default` is permanent and is never pruned, so launching into a new workspace leaves an empty `default` sitting in the list beside the one you are in; and **Workspace ▸ New Workspace** retains its (empty) workspace until its first tab arrives, so one created and then closed unused stays in the list for the rest of the process. Stepping onto either handed `switchToWorkspaceWindow()` a workspace with nothing to show, and it did the only thing it could — opened a window on it. `nextWorkspaceInCycle()` now walks only workspaces that still hold a session tab, which is exact rather than a heuristic: a window closes itself the moment its last tab goes (`_closeWindowAfterLastSession()`), so `group_count > 0` and "there is a window there" are the same condition. The current workspace stays in the list whether or not it is empty, so the walk keeps its place in the order, and with nowhere else to go the shortcut reports **No other workspace is open** instead of conjuring a window. **Workspace ▸ Open Workspace** is deliberately unchanged — clicking a named empty workspace to open a window on it is the point of that menu; `Alt+W` is a cycle between windows, and its ordering still comes from the same helper, so the two cannot disagree about *order*, only about which rows the cycle skips.
- **Terminal Setup now wraps its terminal cards instead of fighting the Workspaces panel for the column.** Two symptoms, one cause. With both right-column panels open, the bottom of step 03 — and with several terminal rows, whole terminal cards — was painted over by the Workspaces card below it; either panel folded on its own looked fine, which is what made it read as a fold bug. Fixing that by making the row honour the card's floor then produced the opposite complaint: expanding a terminal tile squeezed the Workspaces panel. Both come from the same two settings disagreeing — the column sized Terminal Setup's row with `1fr` (take the leftover) while the card carried a `min(520px, 64vh)` floor (never be smaller than this). A grid item taller than its track *overflows* it and does **not** push the following rows down, so whenever the leftover fell under the floor the card spilled into row 2, where a Workspaces card with its own background painted straight over it (measured in page at a 640px frame: a 105px row holding a 520px card, 403px of overlap). Neither setting survives. All three rows are now `auto`: the card wraps exactly the tiles it holds — a set of folded tiles takes only their height — and grows as one is expanded until it hits a cap of one fully expanded tile plus chrome (`min(520px, 58vh)`, down from `calc(100vh - 200px)`), after which `.rows-wrap` scrolls as it always could. Nothing claims the column's leftover space, so Workspaces gets what Terminal Setup does not need, and the column scrolls only when the two genuinely do not fit. Gone with the `1fr` row: the `terminal-setup-folded` class the fold controller put on the column and the rule it fed, which existed only to stop a folded card being stretched by that row, plus two now-inert declarations on `.terminal-card.card-folded` (a `min-height: 0` countering the deleted floor, and a `flex` shorthand on what has always been a grid item).
- **"Maximum 16 terminals allowed" from a button that stops at 8.** **Add Terminal** walks a fixed ladder of counts (1, 2, 3, 4, 6, 8 — a count is only offerable if it has a layout preset in `LAYOUT_COPY`), but both of its refusal messages quoted `max_sessions`, which is the *backend's* per-group session limit and defaults to 16. The message now names the ladder's top, which is 8 unless a lower configured `max_sessions` trims the ladder below that. The dead `selectedCount >= MAX_SESSIONS` pre-check that could never fire on a default config went with it, and the two branches that computed the next count collapsed into one — on an ascending ladder, "the first entry above the current one" already *is* `selectedCount + 1` whenever that count is offered.
- **Two follow-ups to the combined Startup Mode dropdown.** **(1)** An agent's preflight result no longer repaints the whole mode list. The status colours moved onto the combined select as `background-color` + `color`, and a native `<select>` hands both of those down to its popup — so after checking, say, Claude, the open dropdown showed **Terminal**, **Initial Command**, **File Explorer** and **Browser** in that agent's green, orange or red too, as if every mode had a CLI install state. The status now paints the control's frame only (border plus a 1px inset ring); the status *word* was already carried three other ways — the selected option's `· Installed` suffix, the preflight summary chip under the field, and the select's tooltip — none of which changed. The block's per-theme colour literals were replaced by the theme-aware `--gv-success` / `--gv-warning` / `--gv-danger` / `--gv-accent` tokens, so the two `[data-theme="light"]` override blocks are gone. **(2)** Switching a card from an agent to **Browser** no longer lands on `http://claude/`. A draft carries one `initial_command`, which in agent mode holds the agent's name, and the row builder seeded *both* the Initial Command and the Browser URL inputs from that same value — so the hidden URL box was pre-filled with `claude` and the pane launched at that host the moment the mode changed (the value is a valid hostname, so URL normalization accepted it). Each input now seeds only from its own mode; a browser field on any other kind of draft starts at the default `http://127.0.0.1:3000`, which is now one named constant rather than three copies of the literal.
- **The terminal card's agent choice now lives inline in the Startup Mode dropdown, and the card got materially shorter.** The separate Agent select is gone: the startup-mode select carries an `Agent` optgroup with one entry per registry agent (values encoded as `agent:<name>`, plus the custom entry), so one dropdown answers "what does this pane run" in a single pick — the preflight status colours and the "· Installed" suffix moved onto that combined select, and the saved-session payload keeps its separate `startup_mode`/`agent_selection` fields untouched. The auto-mode launch explanation no longer sits as a permanent paragraph inside the checkbox: it hides behind a `?` tip button (the same inline-tip pattern the Shell field uses) and updates in place when the agent changes. Vertical room got the same treatment as horizontal clipping before it: Terminal Setup keeps a floor tall enough to show one fully expanded agent-mode card even with the Workspaces panel open (the column scrolls before step 03 gets crushed), the Workspaces live list scrolls instead of growing the card without bound, and expanding a card scrolls it fully into view — pinning its top when it is taller than the panel. The native launcher window opens 10% larger (1408×924) at 90% content zoom, applied through the existing native-zoom control once the page loads, for ~20% more usable form area.
- **The launcher's Terminal Setup no longer clips its cards at narrow widths, and both right-column panels fold.** At zoomed or narrow window sizes the step-03 card grid overflowed its panel and cut the terminal cards (and their Subdirectory fields) off at the right edge (`docs/images/clipping.png`): each card is a grid that never declared a column, so its implicit `auto` track grew to the content's max-content width and the card's `overflow: hidden` cut off everything past its right edge — fold chevron, status dot, inputs, checkboxes. The cards now pin an explicit `minmax(0, 1fr)` column (and their rows and inputs carry `min-width: 0`), so the content always resolves to the width the panel gives it at any window size or zoom level. On top of that, each terminal card gained a chevron in its head that folds it down to the title row — the whole head is the click target, not just the chevron, with the title input opting out — and a collapsed card hugs its head instead of stretching to an expanded neighbour's height; and cards default to folded when three or more terminals are selected (fold state is view-only, snapshotted across the DOM rebuilds that count changes and session imports trigger, and never written into saved-session payloads). The **Terminal Setup** and **Workspaces** panels themselves fold too, from a chevron in their section heads, persisted in `localStorage` like the theme preference; a folded Terminal Setup releases its stretched `1fr` grid row so no empty hole remains. Inside each card the field stack is now a two-column flow where width allows (Subdirectory and Startup Mode share a row), with the taller conditional blocks (command, agent, shell, distro) still spanning full width. Three smaller courtesies landed alongside: the uppercase field-caption styling no longer leaks into nested check-field labels (the agent auto-mode help and the shell checkboxes read in sentence case again — a check-field is itself a `<label>`, so it inherited the caps), section-head actions now group on the card's right edge instead of `space-between` stranding the middle button mid-card, and the Subdirectory placeholder was shortened to fit the narrow cards, with the full wording moved to the input's tooltip. Also removed: the `--terminal-columns` custom property `buildTerminalRows()` set on every rebuild, which no stylesheet has ever read.

- **Opening a repository-search result now highlights the matched string, not just its line.** Clicking a hit scrolled the Source view to the line and flashed the whole row, which says *where* but not *what*: on a long line the reader still had to hunt for the term they searched for, and had nothing to double-click to carry into Ctrl+F. The exact matched substrings are now painted in the find-match yellow on the opened row, from the column ranges the backend already computes and sends with every hit — so no client-side re-matching, and a regex or whole-word search highlights exactly what the engine matched, including multiple matches on the same line. The paint goes through the CSS Custom Highlight API rather than `<mark>` wrappers, for the same reason the selection occurrence tint does: rewriting the Source DOM is what re-runs the Markdown fold pass and throws away the scroll position, and the hit has just scrolled the view somewhere specific. Its ranges detach with the row when the Source view re-renders, so the paint clears itself on the next file, tab, or find, and it is registered above the occurrence tint so the two do not fight where they overlap. Server offsets count code points and the DOM counts UTF-16 units, so a span whose text does not match is re-found on the row instead of painting the wrong characters. Browsers without the Highlight API get the line flash exactly as before. Unchanged: the hit still does *not* seed a pane-local find — it is one source location, not a second search — so nothing scrolls off to the file's own first match.
- **The Source font now applies to the Diff view too.** Picking Cascadia Code or JetBrains Mono in the appearance menu restyled the Source view and left the Diff beside it in the default Consolas stack — so a split view showed the same file in two different faces. The setting was carried by a `--source-view-font` custom property declared on `.explorer-source-view`, and the diff panel is that element's *sibling*, not its descendant, so there was nothing for it to inherit from. The diff panel now hosts the property itself and carries the same `source-font-*` class, applied by the same `applyExplorerSourceFontToElement()` on render and on every change. Both diff renderers restate the property for the same reason the source rows already did — a more specific declaration was beating the inherited value: the handwritten side-by-side fallback pinned its own Consolas stack, and Diff2Html's vendored CSS pins `.d2h-diff-table` to Menlo (overridden in `terminals.css`, not in the vendored file, so the pinned asset can still be replaced verbatim on upgrade). The commit-diff view, which has no appearance button of its own, picks up the stored preference on open. Nothing else about the setting changed: same allowlist, same `gridvibe.sourceViewFont` preference, same three persistence paths.
- **The last six text glyphs in the explorer are now SVG icons.** The Files tree's expand chevron and its open-folder and open-in-a-new-tab buttons, the Git row's open-containing-folder button, the diff commit-history expand toggle, and the Markdown section fold chevron were still drawing `▾ ▸ ↪ ↗` as button text — so they scaled with the font rather than the icon size, sat off-centre against the stroke icons beside them, and rendered differently per platform depending on which font supplied the arrow. All six now use the same stroke-style `currentColor` SVG language as the rest of the pane. The three chevrons reuse the shared `UI_CHEVRON_*` constants the repo-search groups already use; the two navigation buttons got their own icons (a folder and an external-link arrow) chosen to stay distinguishable from each other and from the Git stage `+`, which is what the two different arrow glyphs were doing before. Behaviour, hit areas, and every `title`/`aria-label` are unchanged.
- **Internal — audit follow-ups.** The find-match yellow is now a single `--gv-match-rgb` token in `tokens.css` instead of being spelled `#facc15` in one rule and `rgba(250, 204, 21, …)` seventeen lines below it. `getGridMetrics` and `getStep2DefaultDirectory` each existed on both pages with quietly different contracts (`getGridMetrics` returned `null` below 4 panes in `terminals.js` and `{columns: 2, rows: 2}` in `launcher.js`); both now live once in `shared.js` on the stricter contract, with the launcher's layout preview keeping its 2×2 floor explicitly. A disconnected pane no longer writes one `WARNING` per keystroke to `logs/gridvibe.log` — the line is diagnostic, the condition already reaches the user through `session_status`, so it logs at DEBUG. `update_session_metadata` gained the `explorer_source_font` field its five sibling field lists already had, so a future route that updates explorer appearance through it will not silently drop the source font. Two page-lifetime collections (`workspaceSaveTargets`, `appliedExplorerMdSessions`) are now pruned when a group or pane genuinely closes — never on a plain group switch, where forgetting the appearance guard would re-apply a saved font over one changed since launch. The dead `ssh.default_port` config key, which nothing has read since the port default was hardcoded, is gone from `default_config.json`. And every citation of the gitignored `docs/r&d/` scratch archive is out of the source tree and the maintained guides: those documents ship with no clone, so the references were unfollowable even where the path was spelled correctly.
- **An explorer pane relaunched on a different root no longer opens onto `[Errno 2] No such file`.** Change the directory of an imported explorer session, launch it, and the pane came up showing a raw backend error with an inert path bar — the breadcrumb was plain text, and only clicking something in the Files tree brought the pane back to life (`docs/images/error_load.png`). Open tabs persist as paths *relative to the pane's root*, so retargeting the root leaves every one of them pointing at a file this explorer does not have. Three things were wrong and each is fixed. **(1)** The launcher carried the saved tab strip through invisibly in the row dataset, including across an edit to the row's directory; the row now records the directory its tabs belong to (`data-explorer-tabs-dir`) and drops `explorer_open_tabs`/`explorer_active_tab`/`explorer_tab_views` as soon as that no longer matches, so retargeting a pane relaunches it clean instead of with another root's tabs. **(2)** The restore opened the saved active tab and, when the fetch failed, left the pane *unattached* — no directory had been loaded, so `renderExplorerDirectoryOpenError()` fell through to replacing the whole viewer with the error text and the breadcrumb never got its clickable crumbs. The restore now opens the tab itself rather than through `activateExplorerTab()` (which reports nothing back), and on failure falls back to a directory listing — the saved Preview directory if it still exists, otherwise the root, which the session guarantees does exist. A tab whose file is genuinely gone is dropped; a tab that failed for any other reason is kept unselected so clicking it retries. **(3)** A missing path answered with the wrong shape entirely: SFTP `normalize()` resolves against the server and fails outright on a path that is not there, so paramiko's `[Errno 2] No such file` surfaced verbatim as a **500**, and the local backend called it "Explorer path is not a file". Both now raise `ExplorerPathNotFoundError` — **404** with a stable `not_found` code and the path named relative to the root — which is what lets the frontend tell "this file is not here" from "the connection hiccuped" and prune only the former. A path that was never inside the root still gets the containment error rather than becoming an existence probe, and the open-file change listener already treated 404 as stop-immediately, so a file deleted while open still parks quietly on the last good view.
- **The Source view has a font of its own, and Consolas is gone from the font lists.** The appearance menu offered a font family for the Markdown preview — the view you *read* — while the Source view, the one you actually stare at code in, was pinned to a single hardcoded stack. It now has its own **Source font** group in the same popover, monospace-only (**Default** keeps the stack it has always used, plus Cascadia Code, JetBrains Mono, Courier New), applied through one `--source-view-font` custom property on the panel, so the highlighted rows and the in-place edit textarea inside it both follow without either being re-rendered. The property is restated on `.explorer-source-line-code` rather than left to inherit: each row's code cell is a `<code>`, the UA stylesheet's `code { font-family: monospace }` matches it *directly*, and a matching UA declaration beats an inherited author value — so with inheritance alone the browser's generic monospace won every row and only the line-number gutter followed the setting. It saves and restores exactly like the preview font: the same bounded allowlist, its own `gridvibe.sourceViewFont` local preference, and the same three persistence paths — saved presets, workspace **Save Session**, and the `runtime_state.json` restart snapshot — as `explorer_source_font`, gated to explorer panes and allowlist-validated on the backend, applied once per session id so a pane rebuild never clobbers a font changed mid-session. Two consequences of the setting no longer being preview-only: the appearance button is shown for **every** file rather than only previewable ones (a file with no preview simply gets the Source group on its own, since the preview settings would change nothing it can show), and the button stays live while editing instead of being dimmed with the rest of the edit-mode chrome — like the zoom and wrap controls beside it, it only restyles the surface, and the font it sets is the one being typed into. **Consolas is retired from both font lists**: the JetBrains Mono stack falls back to Consolas, so on any machine without JetBrains Mono installed the two entries rendered identically. A stored or saved-session `consolas` aliases onto `jetbrains-mono` on both the client and the backend rather than being dropped back to the default, so nobody's saved preference silently resets. Terminal font settings are a separate surface and keep their own list.
- **The coding fonts the pickers name are now shipped with GridVibe.** Following on from the above: *neither* JetBrains Mono nor Cascadia Code is present on a stock Windows install (Cascadia ships inside the Windows Terminal app package, not system-wide), and both stacks end in Consolas — so picking either one, in the explorer's font menu or in App Settings' terminal font list, produced no visible change at all. That is what made Consolas look like a duplicate of JetBrains Mono: it *was* JetBrains Mono, falling back. Both faces are now vendored as latin-subset woff2 (regular + bold, ~100 KB total, SIL OFL-1.1, pinned from `@fontsource` like every other vendored asset, so nothing is fetched from a CDN and the app still works offline) and declared in `tokens.css` — the one stylesheet both pages load, so the explorer and App Settings resolve the same faces instead of each shipping their own copy. Glyphs a face lacks still fall through to the next family in the stack, and italics are synthesized from the regular face. One knock-on: a terminal pane set to a vendored font could be measured against the fallback face and repainted with the real one, leaving its grid a fraction off, so panes re-fit once `document.fonts.ready` resolves; a pane on an installed font measures the same twice and sees nothing.
- **Wrapped diffs now wrap on both sides.** With line wrapping on, the right column reflowed inside the pane while the left column was cut off at the pane's edge — most visibly on files whose hunks sit inside a function or a class. Diff2Html renders each side as its own table, and Git's `@@ -a,b +c,d @@` header carries the enclosing section name (`@@ -120,7 +120,9 @@ def open_explorer_file(...)`) on the **left** side only — the right side gets a blank placeholder. That header's text sits directly in the `nowrap` line div with no `.d2h-code-line-ctn` to wrap inside, so it set the left table's minimum width; every row below it inherited that width, and wrapped mode's `overflow-x: hidden` (it hides the paired horizontal scrollbars, since wrapped text should not need them) clipped the overflow with nothing left to scroll it back. The block header now wraps with the code. Unwrapped mode is untouched: both sides still keep full-width lines and their own sticky scrollbars. Deliberately *not* also pinning the tables with `table-layout: fixed` — that looks like the robust belt-and-braces guard and it is not: fixed layout hands the number column an equal half of the side while the number cell's own `max-width: 4em` still holds its box at 4em, so the gutter paints 4em wide and the remainder of its column renders as a ~390 px blank gap in front of every code line on both sides (`docs/images/diff_empty_space.png`).
- **Long lines keep their intraline diff emphasis.** `maxLineLengthHighlight` was pinned at 2000 characters, below Diff2Html's own 10000 default, and that limit is all-or-nothing: a line past it renders as a plain red/green block with no darker `<ins>`/`<del>` marks on the parts that actually changed, so a one-value edit inside a long line looked like a wholesale rewrite. It bites generated SQL, migrations, seed data, and minified assets hardest — exactly the files where reading the change off the block colour alone is hopeless. The cap now tracks the vendored default. The char diff behind it is O(n·d) in the *edit distance*, not the line length, so the common case (a small edit inside a long line) stays cheap, and the diff payload is still bounded to 256 KiB / 4,000 lines before it ever reaches the renderer. Unchanged: `matchingMaxComparisons` (1500) and Diff2Html's 200-character `maxLineSizeInBlockForComparison`, which decide whether a block's deletions and insertions get *re-paired* before comparison — a block of long lines still pairs them in order.
- **Diff syntax colour is applied once instead of twice.** `renderExplorerDiffWithDiff2Html()` called `ui.highlightCode()` after `ui.draw()`, but `draw()` already highlights when the config sets `highlight: true` — so every diff was highlighted, then highlighted again over its own output, nesting a duplicate `<span class="hljs-…">` inside each span the first pass produced and doing the Highlight.js work for every line of the patch a second time. The intraline `<ins>`/`<del>` markup survived both passes, so this was invisible, but it doubled the render cost of a large diff.
- **A file you can't open can now be downloaded.** Download was reachable only from the file viewer's toolbar, which means it was reachable only for files the viewer can render — exactly the wrong set. An archive, a binary, or anything past the 10 MiB text limit never reaches editor mode, so the one control that would have got it off a remote host sat behind a view that refuses to open. **Download file** now sits in the explorer's right-click menu next to **Copy path** / **Copy relative path**, on Files-tree rows, Preview listing rows, Git **Changes** rows and pinned file tabs, and downloads the row you clicked rather than whatever the viewer happens to hold. It is the same read-only `GET /api/explorer/<id>/download` the toolbar button uses — same 100 MB cap, same root confinement, same pywebview `save_download` bridge in the native window where WebView2 drops anchor downloads — so the read-only explorer contract is untouched. It is offered only where the worktree copy is the file the row names: directory rows, deleted entries, Git rows for a deleted path, and commit-history rows (which show a past commit's version, not the worktree's) don't get the entry rather than getting one that would download the wrong bytes or fail.
- **`Alt+W` no longer dead-ends on a workspace whose terminal was left highlighted.** Cycling through three workspaces stopped at the first one holding a focused pane: every keystroke went into the terminal and the window could only be left with the mouse. Three separate faults, each enough on its own. **(1)** xterm keeps exactly *one* custom key event handler per terminal, and the clipboard wiring installed a second one — silently replacing the pass-throughs `makeTerminal` had set up. xterm then claimed `Alt+W`, sent `ESC w` to the shell, and cancelled the event with `preventDefault()` **and** `stopPropagation()`, so the page-level shortcut never ran at all. The pass-throughs and the copy/paste keys now share a single install (`attachTerminalKeyEventHandler()`), which is also what restored `Ctrl+Shift+F`'s guaranteed path to the scrollback search overlay. **(2)** Even once the key arrived, the shortcut discarded it: `Alt+W` is suppressed over editable targets, and xterm's helper textarea — the keyboard target of every focused pane — is a `<textarea>`. It no longer counts as one for this shortcut, while real inputs (search boxes, name fields, explorer controls) still block the cycle. **(3)** DOM focus survives a window switch, so a workspace left with an active pane came back with that pane focused again. Leaving a workspace now parks the window with nothing selected — both when GridVibe makes the switch (the keybind, **Workspace ▸ Open Workspace**, a session moved to another workspace, a new workspace window, all through one `switchToWorkspaceWindow()` wrapper) and when you simply click another window, which on a second screen is the usual way. - **Selecting a word in the explorer's Source view now tints its other occurrences.** Double-click a word — or drag-select any single-line snippet — and every other occurrence in the open file lights up, the way an editor does. Until now the only way to see them was Ctrl+F, which answered the question but paid for it: it re-rendered the source, so the view snapped back to the file's first match and, in Markdown, unfolded the whole document. The occurrence tint never rewrites the source DOM at all — it is painted with the CSS Custom Highlight API, so folds stay folded, the scroll position stays put, and the selection you just made survives. A selection that is a bare identifier matches whole words only (double-clicking `id` does not light up every `width`), anything else matches as a substring; matching is case-insensitive like the find widget, capped at 500 occurrences, and debounced 90 ms so a drag-select does not rescan on every mouse move. The selected text itself keeps the browser's own selection paint rather than being tinted twice. Browsers without the Highlight API (it needs Chromium 105+/WebView2, Firefox 140+ or Safari 17.2+) simply see no tint — nothing errors, and the find widget stays the explicit fallback.
- **A find seeded from a selection opens on the match you were looking at.** Ctrl+F over a highlighted word used to seed the query and then activate match 1 of N, throwing the Source view back to the top of the file; it now activates the first match at or after the caret's line. The same anchor applies to repo-search hits: clicking a result seeds the in-file find on the line the hit is on instead of scrolling away from it. The seek is consumed once, so paging with Enter/⇧Enter afterwards is unaffected, and typing in the find box is its own starting point.
- **A find no longer unfolds a whole Markdown source.** Collapsed sections were disabled outright while a search was active, so every Ctrl+F threw away the fold state a long document had been read down into. Only the sections that actually contain a match are opened now, and only when a result set is first computed — so collapsing a section during a live find sticks instead of springing back open, and every other fold is left exactly as it was.
