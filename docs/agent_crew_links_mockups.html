Agent Crew Links

When one agent hands tasks to others through GridVibe's tools, nothing on screen says so. The sidebar and the dashboard dialog list every agent as a separate row, so you can't tell which orchestrator a worker reports to, or which workers are still busy on its behalf.

This page proposes three ways to show those links in each surface. Every mockup plays the same scenario: one Claude orchestrator with three workers, one of which hands off a sub-task, plus a second small crew in another workspace. Use the step bar to move through it, and hover rows in the mockups that say they react to hover.

Scenario

What GridVibe already knows

The link data exists on the server today. It just never reaches either dashboard surface.

KnownEvery handed task is an assignment

A task on split_pane, launch_panes or set_pane_agent records the requester pane, the worker pane, when it was handed, whether the worker has read it, and its state: working, reported or ended.

KnownThe worker's own verdict

report_result carries done, failed or blocked, and a report time. A report outlives the worker's pane, so you can close a finished worker without losing its answer.

KnownCrews are trees

A worker with tools can hand off again, up to the depth budget (5 by default). launch_panes opens a new tab, so one crew can span several session cards.

MissingThe payload carries none of it

GET /api/dashboard publishes PANE_FIELDS only. No requester, no worker, no link state.

MissingNobody knows an orchestrator is waiting

An agent sitting inside wait_for_results looks idle or working, depending on its output. The results store can count open waits per requester cheaply.

ConstraintNo spare hue for crews

Session cards already use ten hues that cover the whole wheel, and working is green. A crew can't get a colour of its own without colliding, so these proposals carry crew identity with lines, the orchestrator's mark and the accent.

One visual language for links

Every proposal below draws a link the same way, so the two surfaces read alike. Lines run from the orchestrator to the worker. Motion means a worker is working on a handed task right now; nothing else on a link moves.

Groundwork every option needs

Whichever visuals you pick, the server work is the same and small:

  • A links list in the dashboard payload, one entry per assignment: requester pane, worker pane, state, the worker's verdict, whether it has been read and collected, the two timestamps, and the end reason. Built from an explicit field list like PANE_FIELDS. Never the task text, the report text, the receipt or the handoff id.
  • A waiting reading for orchestrators: the results store counts requesters currently blocked in wait_for_results, and the row's state mark shows the new dotted "waiting on crew" ring.
  • Composed outside the other locks. The results store's lock is already a leaf; the gatherer snapshots it on its own, after activity and the manager, never nested.
  • Lines are a decoration layer. One SVG per surface, painted after the rows from their measured positions. A link changing state repaints the SVG and never rebuilds rows, so scroll, focus and the input-target ring stay put.
  • Motion follows the poll. Animations pause with the hidden-document rule, and under reduced motion the lines hold still and keep their colour and dash pattern.

Sidebar options

The docked sidebar is a sixth of the window. It's where you watch agents while you work, so it needs a reading you get at a glance, without re-learning where rows sit.

S1

Nested rail

effort: medium-large

Workers move under their orchestrator inside the card, indented, joined by a tree rail like a file tree. A worker that lives in another session stays in its own card and gets a stub row under the orchestrator ("1 more in link-tests") plus a back-reference on its own row.

Works well

  • The most familiar shape: parent and children read as one block.
  • Nested hand-offs indent naturally.

Costs

  • Changes row order, which today is the window's own pane order by contract.
  • Cross-session workers become stubs, so the main case for launch_panes crews is the weakest.
  • Rows jump when a handoff is recorded.
S2

Badges and crew highlight

effort: small

Rows stay exactly where they are. The orchestrator gets a crew chip with its count of reported workers ("1/3"). Each worker gets a link chip carrying its orchestrator's mark. Hovering or focusing any crew member dims everything outside its crew and rings the members. The mockup holds the hover on the orchestrator; hover another row to move it.

Works well

  • Cheapest, with no layout change and no lines to measure.
  • Works across sessions and workspaces for free.

Costs

  • At rest you only see chips; the links themselves appear only on hover.
  • No motion, so "both still working" isn't visible at a glance.
  • Two crews by the same agent kind need the hover to tell apart.
S3

Lane gutter

recommendedeffort: medium

A narrow gutter down the sidebar's left edge carries one thin wire per assignment, like the Git sidebar's graph lanes. Each wire leaves the orchestrator's row, runs down the gutter and enters the worker's row, crossing card and workspace boundaries when it has to. Working wires flow; reported ones turn green or amber. Rows never move. The orchestrator also gets S2's crew chip, and hover highlights the crew. Hover a row in the mockup.

Works well

  • Links are visible at rest, and "still working" is visible as motion.
  • Keeps today's row order and card hues untouched.
  • Cross-session crews are drawn as well as same-session ones.

Costs

  • Takes about 18px of width from a narrow column.
  • Past four parallel wires it has to bundle them into one trunk.
  • The layer re-measures on scroll, resize and every rebuild.

Dashboard dialog options

The dialog has width to spare and is opened to take stock, so it can afford a view that explains a crew, not only flags it. Its session cards are one column, which leaves room on the right.

D1

Connector margin

effort: medium

The existing list, unchanged, with curved connectors in a right-hand margin from each orchestrator row to its workers. It's the dialog-sized version of S3, so the two surfaces teach each other. Hover highlights a crew.

Works well

  • Same reading as the sidebar, no new layout.
  • Cheap once S3's layer exists.

Costs

  • Says who is linked, not how far along the crew is.
  • Long crews across bands draw long arcs.
D2

Crew board

recommendedeffort: medium-large

A Crews section at the top of the dialog, shown only while a crew exists. Each crew is a small pipeline: the orchestrator on the left, its workers fanned out to the right, sub-workers further right. Every worker node shows its session, its status pill, and a ghost when its pane closed but its report is kept. The progress bar in the crew header counts reports. The session list stays below, unchanged.

Works well

  • Answers "how far along is this crew" in one look.
  • The only option that shows ended and ghost workers clearly.
  • Leaves the list exactly as it is.

Costs

  • A crew's agents appear twice: on the board and in the list.
  • A new layout with its own empty and narrow-width rules.
D3

Group by crew

effort: medium

A Session / Crew switch in the title bar. Crew mode regroups the same rows into one card per crew with a tree rail, each row tagged with its session hue, and puts every agent outside a crew in a last card.

Works well

  • No duplication; each row appears once.
  • Reuses the row and close-verb code as is.

Costs

  • A second ordering of the same rows, so a remembered row moves between modes.
  • Hides workspace and session structure while it's on.

Cases every option has to handle

Worker in another session or workspaceWires and arcs cross card and band boundaries; both surfaces already list every workspace. Clicking the worker row lands on its pane the way it does today.
Nested hand-offsLanes and rails nest. The sidebar caps visible indentation at two levels and labels deeper workers with a depth chip; the board scrolls sideways.

Worker closed before reportingThe link ends: grey dotted line, a × at the worker end, and the end reason ("pane closed", "relaunched", "task replaced") on hover.
Orchestrator closedThe server drops its assignments, so the lines disappear and the workers carry on as ordinary rows.
Many workersPast four parallel wires, the lane gutter draws one trunk with ticks; the board lists them in one column.
Reduced motion or hidden windowNo flow or pulses; state stays readable from colour, dash pattern and the hover text. Hidden documents pause with the poll.

Recommendation

Build the groundwork first, then:

  1. Sidebar: S3, the lane gutter, with S2's crew chip on orchestrators and the hover highlight. It's the only sidebar option that shows the links and their activity at rest without moving rows.
  2. Dialog: D2, the crew board, above the unchanged list. The dialog is where you go to take stock, and the board is the only view that answers "how far along is this crew".
  3. Later, if wanted: D1's connectors on the dialog list. They reuse S3's layer, so they come cheap once it exists.

S1 and D3 both reorder rows, which runs against the dashboard's order contract and makes rows jump when a task is handed out. I'd skip them.

When does a line move?

You asked for animation when both agents are working. An orchestrator usually sits in wait_for_results while its workers run, so "both working" would rarely be true. The mockups animate while the worker is working, and glow brighter when the orchestrator is waiting on it.

Worker working (+ glow when awaited)Only when both report working
How long do settled links stay?

Reports are kept until the orchestrator's pane closes. Showing every collected link for that long can clutter a long session.

Show panes created without a task?

Panes an agent splits or launches carry a creator stamp even without a task. They could get a faint "created by" link, or none.

Give each task a short label?

Rows show the worker's chat title, which an agent often hasn't set yet. An optional short label on the task (a few words, shown on the board and link hover) would say what each worker is doing. It's a tool-surface change and the label would be published, unlike the task text.
